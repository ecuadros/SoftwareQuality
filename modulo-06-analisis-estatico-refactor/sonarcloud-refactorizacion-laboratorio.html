SonarCloud: un quality gate cross-language

Los linters del Módulo 6 (página anterior) corren por stack, dentro del pipeline de CI (Módulo 5). SonarCloud agrega una capa encima: un único dashboard que combina resultados de análisis estático, cobertura de tests y el índice SQALE de deuda técnica (Módulo 1) — sin importar si el repo es Python, C++, Flutter/Dart o Java/Spring Boot.

.github/workflows/ci.yml — paso agregado al pipeline del Módulo 5
      - name: Análisis SonarCloud
        uses: SonarSource/sonarcloud-github-action@v3
        env:
          GITHUB_TOKEN: ${% raw %}{{ secrets.GITHUB_TOKEN }}{% endraw %}
          SONAR_TOKEN: ${% raw %}{{ secrets.SONAR_TOKEN }}{% endraw %}

SonarCloud comenta directamente en el Pull Request qué código nuevo introduce problemas, y puede configurarse como quality gate obligatorio (Módulo 5): un PR que empeora la cobertura o introduce un code smell "bloqueante" no pasa el check requerido.

Regla práctica de SonarCloud: "Clean as You Code". No exige arreglar toda la deuda técnica histórica del proyecto de una vez (inviable) — exige que el código nuevo de cada PR cumpla el estándar. La deuda vieja se paga gradualmente, solo cuando se toca esa zona del código.

Catálogo breve de refactorización

Refactorizar (Módulo 3: el paso "Refactor" del ciclo TDD) significa mejorar el diseño interno sin cambiar el comportamiento observable — y cada code smell del catálogo anterior tiene una técnica estándar asociada:

Code smellTécnica de refactorIdea central
Long MethodExtract MethodPartir la función grande en varias funciones pequeñas, cada una con un nombre que explica su propósito.
Duplicated CodeExtract Function/ClassMover la lógica repetida a un solo lugar; todos los llamadores reusan esa versión única.
God ClassExtract ClassSeparar responsabilidades distintas en clases distintas, cada una con un motivo de cambio.
Magic NumbersReplace Magic Number with Named ConstantEDAD_MINIMA_LICENCIA = 17 en vez de un 17 suelto.
Condicionales anidados complejosReplace Conditional with PolymorphismReemplazar una cadena larga de if/elif por clases que implementan el mismo método distinto.
Regla de oro: nunca refactorices sin una suite de tests en verde cubriendo ese código primero (Módulo 3). Refactorizar sin red de seguridad no es refactorizar — es reescribir a ciegas y esperar que nada se rompa.

Mutation testing: probar a tus propios tests

En el Módulo 3 quedó pendiente: la cobertura de código no garantiza que las aserciones sean rigurosas. El mutation testing resuelve exactamente eso: una herramienta introduce pequeños cambios artificiales ("mutantes") en tu código — invierte un > por un <, cambia un + por un - — y corre tu suite de tests contra cada mutante.

Resultado del mutanteQué significa
Mutante "muerto"Algún test falló al correr contra el código mutado — tus tests sí detectan ese tipo de error. Bien.
Mutante "sobreviviente"Todos los tests siguieron pasando a pesar del cambio — tus aserciones no son lo suficientemente estrictas para notar la diferencia.
bash — herramientas por stack
# Python
$ mutmut run

# C++
$ mull-runner ./build/tests

# Flutter/Dart
$ dart run mutation_test

# Java/Spring Boot
$ mvn org.pitest:pitest-maven:mutationCoverage

Es una técnica costosa en tiempo de cómputo (corre la suite completa una vez por mutante), así que se usa selectivamente: sobre módulos críticos, no sobre todo el repo en cada PR.

Autoevaluación

Pregunta 1 de 6

¿Qué agrega SonarCloud sobre lo que ya hacen los linters de cada stack corriendo en CI?

Correcto: SonarCloud consolida resultados cross-language en un solo panel y puede actuar como required status check adicional, complementando (no reemplazando) los linters del Módulo 6.
Pregunta 2 de 6

¿Qué significa la regla "Clean as You Code" de SonarCloud mencionada en esta página?

Correcto: exigir arreglar toda la deuda histórica de una vez es inviable en un proyecto real; "Clean as You Code" hace que el estándar aplique al código nuevo, permitiendo adopción incremental.
Pregunta 3 de 6

Según el catálogo de refactorización de esta página, ¿qué técnica corresponde al code smell "God Class"?

Correcto: una God Class concentra demasiadas responsabilidades; Extract Class separa cada responsabilidad en su propia clase, cada una con un solo motivo de cambio.
Pregunta 4 de 6

En mutation testing, ¿qué significa que un "mutante" haya sobrevivido a la suite de tests?

Correcto: un mutante sobreviviente es la señal exacta de una aserción débil — el código cambió su comportamiento y ningún test lo notó, justo el problema de cobertura sin rigor visto en el Módulo 3.
Pregunta 5 de 6

Según la "regla de oro" de esta página, ¿qué debe existir antes de empezar a refactorizar un code smell detectado?

Correcto: refactorizar sin tests que confirmen que el comportamiento no cambió no es refactorizar, es reescribir a ciegas — la red de seguridad de tests (Módulo 3) es lo que hace segura la mejora de diseño.
Pregunta 6 de 6

¿Qué herramienta de mutation testing corresponde al stack Java/Spring Boot según esta página, y cómo se invoca?

Correcto: PIT (pitest) es la herramienta de mutation testing del ecosistema Java, invocada como plugin de Maven — mismo principio que mutmut en Python o mull en C++, solo que integrada al mismo mvn que ya usas para test, cobertura y análisis estático.
