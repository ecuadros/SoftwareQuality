Python — pylint y mypy

Python es de tipado dinámico, así que dos herramientas cubren riesgos distintos: pylint detecta code smells y errores de estilo; mypy verifica anotaciones de tipo antes de ejecutar, algo que el intérprete no hace por sí solo.

.pylintrc — configuración mínima
[MESSAGES CONTROL]
max-line-length=100

[DESIGN]
max-args=5
max-branches=12   # limita indirectamente la complejidad ciclomática (página anterior)
bash
$ pylint validador.py
# validador.py:12:0: R0912: Too many branches (13/12) (too-many-branches)
# Your code has been rated at 8.42/10

$ mypy validador.py
# validador.py:5: error: Argument 1 to "es_valida" has incompatible type "int"; expected "str"
mypy atrapa una categoría entera de bugs (pasar un tipo equivocado) que en Python normal solo aparecería como excepción en tiempo de ejecución — moviendo esa detección tan a la izquierda (Módulo 1) como sea posible sin cambiar de lenguaje.

C++ — clang-tidy y cppcheck

En C++, el análisis estático hace un trabajo extra crítico: detectar patrones que llevan a undefined behavior (memoria mal manejada, punteros colgantes) antes de que un sanitizer o Valgrind (Módulo 7) los encuentre en tiempo de ejecución.

.clang-tidy
Checks: >
  bugprone-*,
  performance-*,
  modernize-use-nullptr,
  cppcoreguidelines-pro-type-member-init
bash
$ clang-tidy validador.cpp -- -std=c++17
# warning: variable 'resultado' is used uninitialized whenever 'if' condition is false
# [clang-analyzer-core.uninitialized.Assign]

$ cppcheck --enable=warning,performance validador.cpp
# (warning) Possible null pointer dereference: ptr
Estas herramientas atrapan una clase de bug que no existe en Python, Dart ni Java (los tres con recolector de basura y sin punteros crudos): memoria liberada dos veces, uso de memoria no inicializada, punteros que apuntan a algo que ya no existe.

Flutter/Dart — dart analyze y very_good_analysis

Dart trae su analizador integrado (dart analyze); very_good_analysis es un conjunto de reglas de lint más estricto que el conjunto por defecto, ampliamente adoptado en la comunidad Flutter.

analysis_options.yaml
include: package:very_good_analysis/analysis_options.yaml

linter:
  rules:
    public_member_api_docs: false   # se puede afinar por proyecto
bash
$ flutter analyze
# warning - lib/validador.dart:8:7 - The value of the local variable 'tmp'
#   is not used - unused_local_variable
# info - lib/carrito.dart:22:1 - Missing documentation for a public member
#   - public_member_api_docs
very_good_analysis es intencionalmente más estricto que lo mínimo necesario para compilar — el objetivo es atrapar en el analizador cosas que, en un equipo grande, terminarían siendo comentarios repetidos de code review (Módulo 2) uno por uno.

Java/Spring Boot — Checkstyle, PMD y SpotBugs

Java divide el trabajo entre tres herramientas con roles distintos: Checkstyle vigila estilo y convenciones; PMD detecta code smells de diseño; SpotBugs analiza el bytecode ya compilado en busca de patrones de bugs reales — null pointers probables, recursos sin cerrar, comparaciones de tipos incorrectas.

checkstyle.xml — fragmento
<module name="Checker">
  <module name="TreeWalker">
    <module name="CyclomaticComplexity">
      <property name="max" value="12"/>
    </module>
    <module name="UnusedImports"/>
  </module>
</module>
bash — Maven
$ mvn checkstyle:check
# [WARN] Validador.java:14: Cyclomatic Complexity is 13 (max allowed is 12).

$ mvn pmd:check
# PMD: Avoid unused private fields such as 'servicioFiltradas'.

$ mvn spotbugs:check
# NP: Possible null pointer dereference in Validador.esValida(String)
A diferencia de los otros tres analizadores de este módulo, SpotBugs analiza bytecode ya compilado, no el código fuente. Eso le permite atrapar patrones que dependen de cómo el compilador realmente traduce el código — a costa de necesitar un build previo antes de poder analizar nada, algo que Checkstyle y PMD no requieren.

Lo que cada uno atrapa mejor

StackHerramientasRiesgo que atrapan mejor que los demás
Pythonpylint + mypyErrores de tipo que el intérprete dinámico no detectaría hasta ejecución.
C++clang-tidy + cppcheckUndefined behavior de memoria — categoría de bug que no existe en los otros tres stacks.
Flutter/Dartdart analyze + very_good_analysisConsistencia de estilo y patrones idiomáticos de widgets a escala de equipo grande.
Java/Spring BootCheckstyle + PMD + SpotBugsPatrones de bug detectables solo en bytecode compilado (SpotBugs), además de estilo y diseño en el código fuente.

Los cuatro, sin embargo, comparten la misma capacidad de detectar code smells genéricos (funciones largas, alta complejidad ciclomática, código duplicado) vistos en la página anterior — esa parte del catálogo es transferible entre lenguajes, aunque la sintaxis de configuración no lo sea.

Autoevaluación

Pregunta 1 de 6

¿Qué detecta específicamente mypy que pylint no está diseñado para detectar?

Correcto: mypy es un verificador de tipos estático para un lenguaje dinámico — su función específica es atrapar errores de tipo antes de que el código se ejecute.
Pregunta 2 de 6

Según esta página, ¿qué categoría de bug atrapan clang-tidy y cppcheck en C++ que simplemente no existe como riesgo en Python, Dart ni Java?

Correcto: Python, Dart y Java corren sobre un runtime con recolector de basura y no exponen punteros crudos al programador, así que esa categoría específica de riesgo de memoria simplemente no aplica ahí.
Pregunta 3 de 6

¿Qué es very_good_analysis en el contexto de un proyecto Flutter?

Correcto: se incluye vía analysis_options.yaml como un paquete de reglas adicionales sobre dart analyze, no como una herramienta separada.
Pregunta 4 de 6

Según la tabla de comparación, ¿qué tipo de análisis SÍ comparten los cuatro stacks, a pesar de usar herramientas distintas?

Correcto: aunque la sintaxis de configuración cambia, el catálogo de code smells genéricos visto en la página anterior es transferible y las cuatro familias de herramientas lo cubren de alguna forma.
Pregunta 5 de 6

En el ejemplo de .pylintrc mostrado, ¿qué relación tiene max-branches=12 con el contenido de la página anterior del módulo?

Correcto: cada rama (if, for, etc.) suma a la complejidad ciclomática vista en la página anterior; limitar max-branches es una forma directa de que el linter avise cuando esa métrica se sale de un rango razonable.
Pregunta 6 de 6

¿Qué hace distinto a SpotBugs de Checkstyle, PMD, y de los analizadores de los otros tres stacks vistos en esta página?

Correcto: a diferencia de Checkstyle y PMD (que analizan el código fuente) y del resto de linters de esta página, SpotBugs opera sobre el .class compilado — eso le permite ver patrones que dependen de cómo el compilador tradujo el código, a costa de necesitar compilar primero.
