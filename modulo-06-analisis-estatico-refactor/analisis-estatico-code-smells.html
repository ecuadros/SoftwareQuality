La función de 800 líneas que nadie quería tocar

En el Módulo 1 viste el ejemplo de mantenibilidad: "una función de 800 líneas que nadie se anima a tocar". Pasa el tiempo: alguien finalmente necesita agregar un caso más, la modifica con cuidado, corre los tests (Módulo 3) y todos pasan. Se hace merge. Una semana después aparece un bug en un caso completamente distinto de esa misma función — nadie notó que la nueva rama de código interactuaba con una condición que estaba a 400 líneas de distancia, dentro del mismo bloque gigante.

Los tests no fallaron porque nadie escribió un test para esa combinación específica — y en una función de 800 líneas con decenas de condiciones anidadas, es prácticamente imposible que alguien piense en todas las combinaciones. El problema real no era el bug puntual: era que el diseño del código hacía inevitable que apareciera uno tarde o temprano.

El análisis estático ataca exactamente esto: detecta las condiciones de diseño que hacen que los bugs sean fáciles de introducir, antes de que aparezca el bug — sin ejecutar el programa, solo examinando su estructura.

Qué es el análisis estático

Un analizador estático examina el código fuente sin ejecutarlo, buscando patrones conocidos como riesgosos: variables no usadas, funciones demasiado largas o complejas, código duplicado, tipos incompatibles, vulnerabilidades conocidas. Es complementario a los tests, no un sustituto:

Tests (Módulos 3-4)Análisis estático
Ejecuta el códigoSíNo
VerificaComportamiento observable para casos específicosEstructura y patrones del código, para todos los casos a la vez
Detecta"Esta función devuelve el resultado equivocado para este input""Esta función es tan compleja que es difícil garantizar que esté bien para todos los inputs"
RequiereQue alguien haya pensado en ese caso de pruebaSolo que exista el código — no requiere imaginar casos

Catálogo breve de code smells

Un code smell (Martin Fowler / Kent Beck) es un síntoma superficial de un problema de diseño más profundo — no rompe el programa hoy, pero predice dificultad para mantenerlo mañana.

Code smellSeñalRiesgo que anticipa
Long MethodUna función de cientos de líneas, como la del ejemplo inicial.Casos límite ocultos, difícil de testear exhaustivamente.
Duplicated CodeEl mismo bloque de lógica copiado en varios lugares.Corriges el bug en una copia y lo olvidas en las otras.
God ClassUna clase que hace de todo: valida, calcula, persiste, notifica.Cualquier cambio en cualquier responsabilidad obliga a tocar esa clase.
Feature EnvyUn método que usa más los datos de otra clase que los propios.La responsabilidad está en el lugar equivocado — señal de mal acoplamiento.
Magic NumbersLiterales sin nombre en medio del código (if edad > 17).Nadie sabe si 17 es una regla de negocio importante o un valor arbitrario.
Dead CodeCódigo que ya no se ejecuta nunca, pero sigue en el repo.Confunde a quien lee, y a veces esconde bugs "reactivados" sin querer.

Complejidad ciclomática: medir "Long Method" con un número

La complejidad ciclomática (Thomas McCabe, 1976) cuenta la cantidad de caminos independientes que puede tomar una función: cada if, for, while, case o condición lógica adicional suma uno. Una función sin ninguna bifurcación tiene complejidad 1.

ejemplo — complejidad ciclomática = 4
def clasificar_envio(peso, es_urgente, destino_internacional):
    if peso > 30:                        # +1
        return "carga_pesada"
    if es_urgente:                       # +1
        return "urgente"
    if destino_internacional:            # +1
        return "internacional"
    return "estandar"                    # base = 1
Complejidad ciclomáticaInterpretación
1-10Simple, fácil de testear con pocos casos.
11-20Moderada — vale la pena revisar si se puede simplificar.
> 20Alta — el número de casos de prueba necesarios para cubrir todos los caminos crece rápido; candidata fuerte a refactor (siguiente página).
El número no es un juicio moral sobre quien escribió el código — es una señal objetiva y barata de calcular para decidir dónde mirar primero quien va a refactorizar, en vez de adivinar.

Autoevaluación

Pregunta 1 de 5

En el ejemplo de la función de 800 líneas, ¿por qué los tests unitarios existentes no atraparon el nuevo bug?

Correcto: los tests solo cubren los casos que alguien imaginó. Una función con muchas condiciones anidadas hace prácticamente imposible imaginar todas las combinaciones relevantes — ese es precisamente el riesgo que el análisis estático puede señalar sin necesidad de imaginar casos.
Pregunta 2 de 5

¿Cuál es la diferencia clave entre lo que verifican los tests y lo que verifica el análisis estático?

Correcto: son complementarios — uno verifica comportamiento observado en casos concretos, el otro examina patrones de diseño riesgosos en todo el código, sin necesidad de ejecutar nada.
Pregunta 3 de 5

Un método casi no usa los atributos de su propia clase, pero constantemente llama y opera sobre los datos de otra clase distinta. ¿Qué code smell describe mejor esta situación?

Correcto: Feature Envy señala que la responsabilidad de ese método probablemente pertenece a la otra clase, cuyos datos usa más — es una pista de mal acoplamiento.
Pregunta 4 de 5

Según el ejemplo de clasificar_envio, ¿cuál es su complejidad ciclomática y por qué?

Correcto: la complejidad ciclomática parte de una base de 1 y suma 1 por cada punto de decisión — los tres if independientes suman 3, dando un total de 4.
Pregunta 5 de 5

¿Para qué sirve principalmente medir la complejidad ciclomática de una función, según esta página?

Correcto: es una métrica objetiva para priorizar dónde mirar, no un juicio de valor — herramientas como SonarCloud (siguiente módulo dentro de esta unidad) la calculan automáticamente en cada PR.
