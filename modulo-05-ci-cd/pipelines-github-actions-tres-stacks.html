Anatomía de un workflow de GitHub Actions

Un archivo en .github/workflows/*.yml define cuándo correr (on:) y qué pasos ejecutar (jobs → steps). Los tres pipelines de abajo comparten esta forma:

.github/workflows/ci.yml — esqueleto común
name: CI

# corre en cada push a main y en cada Pull Request
on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      # ... pasos específicos del stack, ver abajo ...
// stack 1 de 3

Python — pip + pytest

.github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: "pip"

      - name: Instalar dependencias
        run: pip install -r requirements.txt

      - name: Correr tests con cobertura
        run: coverage run -m pytest --junitxml=results.xml

      - name: Verificar umbral de cobertura
        run: coverage report --fail-under=80
cache: "pip" reutiliza el caché de dependencias entre corridas — no del entorno de ejecución en sí, que sigue siendo limpio cada vez, solo evita re-descargar paquetes ya conocidos.
// stack 2 de 3

C++ — CMake + CTest

.github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Instalar GoogleTest y lcov
        run: sudo apt-get update && sudo apt-get install -y libgtest-dev lcov

      - name: Configurar CMake
        run: cmake -B build -DCMAKE_CXX_FLAGS="--coverage"

      - name: Compilar
        run: cmake --build build

      - name: Correr tests
        run: ctest --test-dir build --output-on-failure

      - name: Generar reporte de cobertura
        run: |
          lcov --capture --directory build --output-file coverage.info
          lcov --summary coverage.info
El paso extra que no tienen Python ni Dart: "Compilar" es su propia etapa, separada de "Correr tests". Si el build falla, el job entero falla ahí — antes de intentar ejecutar un solo test.
// stack 3 de 3

Flutter/Dart — subosito/flutter-action

.github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: subosito/flutter-action@v2
        with:
          flutter-version: "3.24.0"
          channel: "stable"

      - name: Instalar dependencias
        run: flutter pub get

      - name: Analizar código estáticamente
        run: flutter analyze

      - name: Correr tests con cobertura
        run: flutter test --coverage

      - name: Verificar umbral de cobertura
        run: |
          sudo apt-get install -y lcov
          lcov --summary coverage/lcov.info

Nota que flutter analyze aparece aquí como parte natural del pipeline — el análisis estático (Módulo 6) no es una etapa separada y opcional, es parte del mismo gate que los tests.

// resumen

Lo que cambia entre los tres pipelines

PythonC++Flutter/Dart
Action de setupactions/setup-pythonNinguna oficial — se instalan paquetes del sistema a manosubosito/flutter-action
Etapa de build separadaNo — es interpretadoSí, obligatoria antes de testearNo — el análisis y test corren directo sobre el código fuente
Duración típicaRápida (1-2 min)Más lenta (3-8 min) por la compilaciónRápida-media (2-4 min)
CacheablePaquetes pipArtefactos de compilación (ccache)Paquetes pub y SDK de Flutter
En un proyecto que usa los tres stacks en paralelo (poco común, pero posible como ejercicio de este curso), cada uno vive en su propio archivo de workflow — no se fuerza un solo pipeline "universal" que termine siendo peor para los tres.

Autoevaluación

Pregunta 1 de 5

¿Qué evento dispara los tres workflows mostrados en esta página?

Correcto: el bloque on: push / pull_request hace que el pipeline corra tanto en cada PR (para el quality gate) como al fusionarse a main.
Pregunta 2 de 5

Según esta página, ¿qué etapa tiene el pipeline de C++ que no aparece como paso separado en Python ni en Flutter/Dart?

Correcto: al ser un lenguaje compilado, C++ necesita una etapa de build explícita que puede fallar antes de siquiera intentar ejecutar un test — Python y Dart, interpretados, no tienen ese paso.
Pregunta 3 de 5

En el workflow de Flutter/Dart mostrado, ¿qué action se usa específicamente para instalar el SDK de Flutter en el runner?

Correcto: subosito/flutter-action es la action estándar de la comunidad para instalar una versión específica del SDK de Flutter en el runner de GitHub Actions.
Pregunta 4 de 5

¿Por qué en el pipeline de Flutter/Dart, flutter analyze corre como parte del mismo gate que los tests, en vez de ser un paso "opcional" aparte?

Correcto: como se señala en la página, integrar el análisis estático directo en el pipeline (en vez de dejarlo como un paso opcional) es justo lo que lo convierte en parte real del quality gate — tema que se profundiza en el Módulo 6.
Pregunta 5 de 5

Según la tabla de comparación, ¿por qué el pipeline de C++ suele tardar más en total que el de Python?

Correcto: la etapa de build agrega tiempo real de compilación al pipeline, algo que los lenguajes interpretados (Python, Dart) no necesitan pagar en cada corrida.
