// el problema

"En mi máquina funciona"

Un desarrollador corre sus tests localmente, todos en verde, hace merge a main. Dos horas después, un compañero hace git pull para empezar su día y su build falla: la versión de una dependencia que el primer desarrollador tenía instalada localmente (pero nunca declaró en el archivo de dependencias) no coincide con la que se resuelve limpia. El código nunca estuvo realmente probado en un entorno limpio — solo en la máquina de una persona, con su historial acumulado de instalaciones manuales.

El costo real: no es solo la hora perdida del compañero. Es que main quedó roto para todo el equipo hasta que alguien lo detecta y corrige — y branch protection (Módulo 1) no puede evitarlo si nadie corrió los tests en un entorno controlado antes del merge.

Integración Continua (CI) resuelve esto ejecutando build y tests automáticamente, en un entorno limpio e idéntico cada vez, en cada push y cada Pull Request — antes de que el código llegue a main, no después.

// vocabulario que se confunde seguido

Integración continua vs. entrega/despliegue continuo

"CI/CD" junta tres prácticas relacionadas pero distintas. Distinguirlas importa porque cada una resuelve un riesgo diferente:

PrácticaQué automatizaPregunta que responde
Continuous Integration (CI)Build + suite de tests en cada push/PR.¿Este cambio rompe algo, en un entorno limpio?
Continuous DeliveryEmpaquetar y dejar el artefacto listo para desplegar en cualquier momento, con un clic humano.¿Podríamos desplegar esto ahora mismo, si quisiéramos?
Continuous DeploymentDespliegue automático a producción si todo pasa, sin intervención humana.¿Cada cambio que pasa el pipeline llega solo a producción?
Para el proyecto de este curso: el foco es CI — es la base sin la cual las otras dos no tienen sentido, y es lo que vas a construir de verdad en este módulo. Delivery/Deployment automático son la extensión natural una vez que confías en tu pipeline de CI.
// las piezas

Anatomía de un pipeline

Sin importar el stack, un pipeline de CI encadena las mismas etapas conceptuales, cada una fallando rápido si algo está mal (fail fast) para no gastar minutos de cómputo en pasos posteriores inútiles:

  1. Checkout. Clona el commit exacto que disparó el pipeline.
  2. Instalar dependencias. Desde cero, en un entorno limpio — nunca reusando el caché "sucio" de una máquina local.
  3. Build. Compilar (C++), o simplemente verificar que el proyecto importa/arranca sin errores (Python, Dart).
  4. Test. Correr la suite completa: unitarios (Módulo 3), integración y BDD (Módulo 4).
  5. Análisis y cobertura. Linter, cobertura mínima — el Módulo 6 profundiza esta etapa.
  6. (Opcional) Deploy. Solo si todo lo anterior pasó.
// donde por fin se activa la regla del módulo 1

Quality gates: el CI que por fin llena la regla del Módulo 1

En el Módulo 1 activaste Require status checks to pass before merging en branch protection, sabiendo que quedaría vacío hasta este módulo. Un quality gate es exactamente eso: una condición automática (tests en verde, cobertura mínima, cero vulnerabilidades críticas) que un PR debe cumplir antes de poder fusionarse — GitHub la marca como required check y el botón de merge queda bloqueado hasta que pasa.

Esta es la diferencia entre "tenemos tests" y "los tests importan": si un PR puede fusionarse con tests en rojo, la suite es decorativa. El quality gate es lo que hace la disciplina de calidad obligatoria por herramienta, no por buena voluntad — el mismo principio que branch protection y CODEOWNERS en el Módulo 2.
// autoevaluación

Autoevaluación

Pregunta 1 de 5

En el ejemplo de "en mi máquina funciona" de esta página, ¿cuál fue la causa raíz de que main quedara roto?

Correcto: la suite pasó localmente porque la máquina tenía un estado no declarado (una versión de dependencia instalada manualmente). Sin un entorno limpio y reproducible, "pasa en mi máquina" no garantiza nada sobre otros entornos.
Pregunta 2 de 5

¿Cuál es la diferencia principal entre Continuous Delivery y Continuous Deployment?

Correcto: ambos automatizan el empaquetado del artefacto; la diferencia está en si el último paso a producción requiere una decisión humana (Delivery) o es completamente automático (Deployment).
Pregunta 3 de 5

Según la anatomía de un pipeline descrita en esta página, ¿por qué es importante que las etapas fallen rápido ("fail fast")?

Correcto: si el build falla, no tiene sentido correr tests sobre un binario que no compiló; fallar rápido ahorra tiempo y hace más claro dónde está el problema.
Pregunta 4 de 5

¿Qué regla de branch protection, activada desde el Módulo 1, es la que un quality gate de CI termina de habilitar?

Correcto: esa regla quedó activada pero vacía en el Módulo 1 porque no existía ningún pipeline que reportara un check. El pipeline de este módulo es lo que finalmente la llena de contenido real.
Pregunta 5 de 5

¿Por qué se dice que un quality gate hace la disciplina de calidad "obligatoria por herramienta y no por buena voluntad"?

Correcto: es el mismo principio de branch protection y CODEOWNERS del Módulo 2 — la calidad se protege con un mecanismo automático, no confiando en que cada persona recuerde correr los tests antes de fusionar.
