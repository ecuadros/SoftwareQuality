// la metáfora

Una metáfora financiera, no un insulto

El término lo acuñó Ward Cunningham en 1992: escribir código de la forma más rápida posible (en vez de la mejor forma que conoces) es como pedir un préstamo. Te da velocidad hoy, pero genera interés — cada cambio futuro sobre ese código cuesta un poco más mientras la deuda no se pague.

Lo que Cunningham no dijo: "deuda técnica" no significa "código malo" ni "atajo irresponsable". Un equipo puede decidir a propósito tomar deuda para validar una hipótesis de negocio rápido — eso es una decisión técnica legítima, siempre que quede registrada y visible, no escondida. El problema nunca es tomar la deuda; es no saber cuánta tienes.
// clasificación

El cuadrante de Martin Fowler

Martin Fowler propuso clasificar la deuda en dos ejes: si fue deliberada o inadvertida, y si fue prudente o imprudente. El cuadrante importa porque cada tipo se gestiona distinto.

DeliberadaInadvertida
Prudente "Sabemos que este diseño no escala a 1M de usuarios, pero necesitamos validar el producto con 100 esta semana." "Ahora que lo construimos, vemos que debimos haberlo diseñado distinto." (aprendizaje normal)
Imprudente "No tenemos tiempo para tests, ya los escribiremos después." (casi nunca se escriben) "¿Qué es un patrón de diseño?" (falta de experiencia del equipo)

La deuda prudente-deliberada es sana si se documenta y se paga. La imprudente-inadvertida es la que hunde proyectos, porque nadie sabe que existe hasta que el sistema es imposible de cambiar.

// hacerla visible

Cómo se mide (sin adivinar)

No puedes priorizar lo que no puedes ver. Formas concretas de hacer visible la deuda técnica, de más simple a más formal:

  • Marcadores en el código — comentarios // TODO / // FIXME rastreables con grep -rn "TODO\|FIXME" .; útil pero se vuelve invisible si nadie los revisa.
  • Issues etiquetados — un issue de GitHub con label deuda-tecnica, con contexto de por qué se tomó y qué costaría pagarla. Es lo que vas a usar en este curso.
  • Análisis estático automatizado — herramientas como SonarQube calculan un índice SQALE: tiempo estimado para arreglar todos los code smells detectados, expresado en horas/días. Lo vas a integrar en el Módulo 6.
  • Ratio deuda/tamaño — tiempo estimado de remediación dividido entre tiempo estimado de desarrollo total. Sirve para comparar la salud relativa de distintos módulos o proyectos.
// decisión de equipo

¿Pagarla ahora o vivir con ella?

No toda deuda merece pagarse. Antes de agendar una "semana de refactor", pregúntate:

Señales de que esta deuda sí urge pagarse
Si marcaste 0-1: probablemente puedes seguir viviendo con esa deuda. Si marcaste 3-4: es candidata fuerte para priorizar antes de seguir construyendo encima. Código con deuda que casi nunca se toca no está generando interés activo — no es la prioridad, aunque "se vea feo".
// autoevaluación

Autoevaluación

Un equipo lanza una función de emergencia sin tests para cumplir un deadline legal, y crea un issue documentando exactamente qué se omitió y por qué. ¿Cómo se clasifica esta deuda en el cuadrante de Fowler?

Correcto: es deliberada porque el equipo sabía exactamente lo que estaba haciendo, y prudente porque la decisión fue razonable dado el contexto (deadline legal) y quedó documentada para pagarse después. Habría sido imprudente si nadie hubiera dejado registro de la omisión.
