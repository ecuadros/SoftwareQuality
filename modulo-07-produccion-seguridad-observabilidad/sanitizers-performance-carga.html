El test que pasó y el programa que igual estaba roto

Recuerda la pregunta 5 del Módulo 3: un test en verde en C++ no garantiza ausencia de undefined behavior. Aquí está el ejemplo completo. Una función accede a un índice de un arreglo que está apenas un elemento fuera de rango:

buggy.cpp
int obtener_ultimo(const std::vector<int>& datos) {
    return datos[datos.size()];  // debería ser datos.size() - 1
}
El test correspondiente puede pasar igual. Leer un byte fuera de un arreglo no siempre produce un crash inmediato — a veces lee memoria "vecina" que por casualidad tiene un valor parecido al esperado. El comportamiento es indefinido: puede funcionar en tu máquina, en tu versión del compilador, con esos datos específicos — y fallar de forma impredecible en producción, con otra versión del compilador o de la librería estándar.

Los sanitizers y Valgrind existen exactamente para esto: detectan el acceso indebido a memoria en el momento en que ocurre, sin importar si por casualidad el resultado "se ve bien".

// instrumentación en tiempo de compilación

Sanitizers: ASan y UBSan en C++

Los sanitizers de Clang/GCC recompilan tu código agregando verificaciones automáticas en cada acceso a memoria. AddressSanitizer (ASan) detecta accesos fuera de rango, use-after-free y fugas; UndefinedBehaviorSanitizer (UBSan) detecta overflow de enteros, divisiones por cero y otros comportamientos indefinidos del estándar de C++.

bash — compilar con sanitizers
$ cmake -B build -DCMAKE_CXX_FLAGS="-fsanitize=address,undefined -g"
$ cmake --build build
$ ./build/mi_programa
salida de ASan sobre buggy.cpp
==12345==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x...
READ of size 4 at 0x... thread T0
    #0 obtener_ultimo(std::vector<int> const&) buggy.cpp:2
    #1 main main.cpp:8

0x... is located 0 bytes after a region of size 12 allocated here
ASan y UBSan corren dentro de tu suite de tests existente (Módulo 3) — no son una herramienta separada que necesite casos de prueba nuevos. Compilas los mismos tests con las flags de arriba y, si algún test ejercita el bug, el sanitizer lo reporta con la línea exacta, en vez de que el test simplemente "pase por casualidad".
// instrumentación en tiempo de ejecución

Valgrind: fugas de memoria en detalle

A diferencia de los sanitizers (que requieren recompilar), Valgrind ejecuta tu binario ya compilado dentro de una máquina virtual que intercepta cada operación de memoria. Es más lento, pero no requiere cambiar el build — útil para correrlo puntualmente sobre un binario de producción.

bash
$ valgrind --leak-check=full ./build/mi_programa
==12345== HEAP SUMMARY:
==12345==     in use at exit: 40 bytes in 1 blocks
==12345==   total heap usage: 3 allocs, 2 frees, 1,064 bytes allocated
==12345==
==12345== 40 bytes in 1 blocks are definitely lost in loss record 1 of 1
==12345==    at 0x...: malloc
==12345==    by 0x...: crear_buffer() (buggy.cpp:15)

definitely lost significa que esa memoria ya no tiene ningún puntero que la referencie — una fuga real, que en un servidor de larga duración crece hasta agotar la memoria disponible.

Pruebas de carga y performance por stack

Un sistema puede estar libre de bugs de memoria y aun así fallar bajo carga real. Cada stack de este curso ataca esa pregunta con una herramienta distinta, según dónde vive el riesgo:

bash — Python/API: k6
$ k6 run carga.js
#      ✓ status es 200
#      http_req_duration..: avg=45ms p(95)=120ms
#      http_reqs..........: 12000 requests in 30s
StackHerramientaQué mide
Pythonk6 (o Locust)Latencia y throughput de una API bajo N usuarios virtuales simultáneos.
Java/Spring BootGatling o JMeter, más /actuator/metricsIgual que k6, más métricas internas expuestas por Spring Boot Actuator (uso de conexiones, latencia por endpoint) durante la carga.
Flutter/DartFlutter DevTools (pestaña Performance)Frames por segundo y "jank" — cuadros que tardan más de 16ms y rompen la fluidez visual.
C++Perfilado con perf / benchmarks con Google BenchmarkTiempo de CPU por función, útil cuando el riesgo es cómputo intensivo, no una API con usuarios concurrentes.
No es casualidad que cada stack use una herramienta distinta: el riesgo de performance de una API REST (Python), una app móvil (Flutter) y una librería de cómputo (C++) es un problema distinto en cada caso — "performance" no es una sola métrica, es "lo que le importa a ese sistema en particular".

Autoevaluación

Pregunta 1 de 5

En el ejemplo de obtener_ultimo, ¿por qué el test correspondiente puede pasar en verde aunque el código tenga un bug real de memoria?

Correcto: undefined behavior no significa "siempre falla" — significa que el estándar no garantiza ningún comportamiento específico, lo que incluye "funcionar como si nada" hasta que deja de hacerlo.
Pregunta 2 de 5

¿Qué diferencia principal hay entre usar sanitizers (ASan/UBSan) y usar Valgrind?

Correcto: esa diferencia explica por qué Valgrind es más lento pero más flexible (no exige rebuild), mientras los sanitizers son más rápidos pero requieren instrumentar el build.
Pregunta 3 de 5

En la salida de Valgrind mostrada, ¿qué significa que 40 bytes estén marcados como definitely lost?

Correcto: "definitely lost" es la categoría más clara de fuga de memoria — memoria reservada que nunca se libera y a la que ya no se puede acceder, justamente lo que agota recursos en servidores de larga duración.
Pregunta 4 de 5

Según la tabla de herramientas de performance, ¿qué mide específicamente Flutter DevTools que no mide k6?

Correcto: k6 mide performance de APIs bajo carga de red; Flutter DevTools mide la fluidez visual real de una app en un dispositivo — son riesgos de performance distintos según el tipo de sistema.
Pregunta 5 de 5

¿Por qué esta página usa una herramienta de performance distinta para cada stack, en vez de una sola herramienta universal?

Correcto: el riesgo de performance de una API REST, una app móvil y una librería de cómputo intensivo son problemas distintos — cada herramienta está diseñada para medir lo que realmente importa en cada contexto.
