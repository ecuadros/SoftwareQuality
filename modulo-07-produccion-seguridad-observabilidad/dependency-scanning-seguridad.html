El incidente que puso esto en el mapa

En diciembre de 2021, una vulnerabilidad crítica de ejecución remota de código (Log4Shell, CVE-2021-44228) apareció en Log4j, una librería de logging de Java usada — directa o transitivamente — en una fracción enorme del software empresarial del planeta. No era un bug en el código de ninguna de las empresas afectadas: era un bug en una dependencia de una dependencia de una dependencia, tan profundo en el árbol de paquetes que muchos equipos ni sabían que la usaban.

La lección no es "usen menos librerías". Nadie reescribe su propio parser JSON o su propio cliente HTTP — depender de librerías es la forma normal y correcta de construir software. La lección es que tu superficie de riesgo de seguridad incluye código que nunca leíste, y que necesitas una forma automática de saber cuándo una de esas dependencias tiene una vulnerabilidad conocida — no enterarte por las noticias.

Dependency scanning (también llamado SCA, Software Composition Analysis) es exactamente esa forma automática: una herramienta que compara las versiones exactas de tus dependencias contra bases de datos públicas de vulnerabilidades conocidas (CVE) y te avisa antes de que sea un incidente.

// vocabulario

Qué es dependency scanning (SCA)

A diferencia del análisis estático del Módulo 6 (que examina tu código en busca de code smells), el dependency scanning examina el código de terceros que declaraste en tu archivo de dependencias (requirements.txt, pom.xml, pubspec.yaml, conanfile.txt), incluyendo dependencias transitivas — las que tus dependencias directas traen consigo, sin que tú las hayas elegido.

Herramientas por stack

La madurez de esta práctica no es pareja entre ecosistemas — vale la pena decirlo explícitamente en vez de fingir que los cuatro stacks están igual de bien servidos.

Python — pip-audit

bash
$ pip-audit
# Found 1 known vulnerability in 1 package
# Name     Version  ID                  Fix Versions
# -------- -------- ------------------- ------------
# requests 2.25.1   GHSA-j8r2-6x86-q33q 2.31.0

Java/Spring Boot — OWASP Dependency-Check

bash — Maven
$ mvn org.owasp:dependency-check-maven:check
# [WARN] jackson-databind-2.9.8.jar: CVE-2019-12384 (CVSS 8.1) — deserialización insegura
# genera target/dependency-check-report.html con el detalle

Flutter/Dart — Dependabot + dart pub outdated

El ecosistema pub no tiene todavía un escáner de CVEs dedicado tan establecido como los anteriores. La combinación práctica es GitHub Dependabot (que sí entiende pubspec.yaml y abre PRs automáticos cuando hay una versión con fix de seguridad) más una revisión manual periódica de versiones desactualizadas:

bash
$ dart pub outdated
# Package Name  Current  Upgradable  Resolvable  Latest
# http          0.13.3   0.13.6      0.13.6      1.2.2
El caso más honesto: C++. No existe un registro central de paquetes equivalente a PyPI, npm o Maven Central, así que tampoco existe una base de datos de vulnerabilidades tan bien conectada a las versiones exactas que usas. La práctica real en proyectos C++ serios es más manual: revisar avisos de seguridad de las librerías que usas directamente (OpenSSL, Boost, etc.) y, si empaquetas tu aplicación en un contenedor para el Módulo 5, escanear la imagen final con una herramienta como Trivy, que sí tiene buena cobertura de paquetes del sistema operativo instalados en la imagen.
// cuando la alerta llega de verdad

Qué hacer cuando aparece una vulnerabilidad

Ninguna alerta de CVE se resuelve sola. El proceso, siempre en este orden:

  1. ¿Me afecta de verdad? Una vulnerabilidad en una función que nunca llamas tiene prioridad distinta a una en tu ruta crítica de autenticación.
  2. ¿Existe una versión con el fix? Si sí, actualizar y correr la suite completa de tests (Módulos 3-4) antes de hacer merge — un upgrade de dependencia es un cambio real, no un detalle administrativo.
  3. Si no existe fix todavía, documenta la decisión como deuda técnica (Módulo 1) con un Issue explícito, igual que cualquier otro riesgo aceptado a propósito.
Igual que en el Módulo 5, esto se vuelve un quality gate real cuando el scanner corre dentro del pipeline de CI y bloquea el merge ante una vulnerabilidad crítica sin excepción manual — no cuando alguien "se acuerda de revisarlo cada tanto".

Autoevaluación

Pregunta 1 de 5

Según el ejemplo de Log4Shell, ¿por qué muchos equipos afectados ni siquiera sabían que usaban la librería vulnerable?

Correcto: las dependencias transitivas (las que tus dependencias directas traen consigo) son parte de tu superficie de riesgo aunque nunca las hayas elegido ni leído — por eso el dependency scanning examina el árbol completo, no solo tu requirements.txt de primer nivel.
Pregunta 2 de 5

¿Cuál es la diferencia principal entre el análisis estático del Módulo 6 y el dependency scanning de esta página?

Correcto: son complementarios — uno protege la calidad de lo que tú escribiste, el otro protege contra vulnerabilidades conocidas en lo que instalaste.
Pregunta 3 de 5

Según esta página, ¿por qué el dependency scanning en C++ es distinto (y más manual) que en Python, Java o Flutter/Dart?

Correcto: la fragmentación del ecosistema de paquetes de C++ (sin un registro central) hace que la práctica real dependa más de revisión manual de avisos de seguridad y de escanear la imagen final con herramientas como Trivy.
Pregunta 4 de 5

Según el proceso descrito en esta página, si aparece una alerta de CVE pero todavía no existe una versión con el fix, ¿qué se debe hacer?

Correcto: conecta directamente con la deuda técnica prudente-deliberada del Módulo 1 — el riesgo se acepta a propósito, pero queda registrado y visible, no escondido.
Pregunta 5 de 5

¿Qué hace que el dependency scanning se convierta en un verdadero quality gate, según el callout final de esta página?

Correcto: igual que los quality gates del Módulo 5, la protección real viene de que la herramienta bloquee automáticamente, no de que alguien recuerde revisarlo periódicamente.
