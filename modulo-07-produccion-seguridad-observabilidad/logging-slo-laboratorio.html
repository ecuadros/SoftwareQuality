// el problema

"Creo que falló como a las 3 de la tarde"

Un cliente reporta que su compra falló ayer por la tarde. El log del servidor tiene miles de líneas de texto libre como "procesando pago..." y "error al procesar", sin id de transacción, sin marca de tiempo consistente, sin identificar a qué usuario pertenecía. Encontrar esa falla específica entre miles de líneas parecidas, escritas por distintos desarrolladores en distintos formatos, se convierte en arqueología en vez de en una búsqueda de dos minutos.

El costo no es solo el tiempo perdido buscando — es que, cuando por fin ocurre un incidente serio en producción (Módulo 8), la calidad de tus logs determina si el postmortem tiene datos reales o especulación. Este es, otra vez, "shift left" (Módulo 1): invertir en logging estructurado antes del incidente es mucho más barato que reconstruir qué pasó después.
// texto libre vs. datos consultables

Logging estructurado por stack

Logging estructurado significa emitir cada evento como un objeto con campos consistentes (JSON, típicamente) en vez de una oración de texto libre — así una herramienta de observabilidad puede filtrar, agregar y alertar sobre esos campos, no adivinar parseándolos.

Python — structlog
import structlog
log = structlog.get_logger()

log.info("pago_procesado", usuario_id=42, monto=108.00, cupon="VIP10")
# {"event": "pago_procesado", "usuario_id": 42, "monto": 108.0, "cupon": "VIP10", "timestamp": "..."}
Java/Spring Boot — Logback + logstash-encoder
log.info("pago_procesado usuario_id={} monto={} cupon={}", usuarioId, monto, cupon);
// con LogstashEncoder configurado, Logback emite JSON automáticamente:
// {"message": "pago_procesado...", "usuario_id": 42, "monto": 108.0, "level": "INFO"}
C++ — spdlog
{% raw %}// fmt (la librería detrás de spdlog) usa {} como placeholder,
// por eso las llaves literales del JSON se escapan como {{ y }}
spdlog::info(R"({{"event": "pago_procesado", "usuario_id": {}, "monto": {}}})", usuarioId, monto);{% endraw %}
Flutter/Dart — logger + envío a un backend de observabilidad
logger.i(jsonEncode({
  'event': 'pago_procesado',
  'usuario_id': usuarioId,
  'monto': monto,
}));
En Spring Boot, esto se complementa con Spring Boot Actuator: expone endpoints como /actuator/health y /actuator/metrics que ya traen métricas estándar (uso de memoria, conexiones activas, latencia por endpoint) sin necesidad de instrumentar cada una a mano.
// del log individual a la promesa del sistema

SLIs, SLOs y error budget

Un log cuenta la historia de un evento. Un SLI (Service Level Indicator) resume miles de esos eventos en un número: "porcentaje de requests que respondieron en menos de 200ms", "porcentaje de requests exitosos". Un SLO (Service Level Objective) es la meta que tu equipo se compromete a cumplir sobre ese SLI.

SLO de disponibilidadTiempo de falla permitido al mes
99% ("dos nueves")~7.3 horas
99.9% ("tres nueves")~43 minutos
99.99% ("cuatro nueves")~4.3 minutos
Ese tiempo de falla permitido es tu error budget. No es un fracaso gastarlo — es una herramienta de decisión: si ya gastaste el presupuesto del mes, el equipo prioriza estabilidad sobre features nuevas. Si sobra presupuesto, hay margen para asumir más riesgo. Sin un SLO explícito, esa conversación se vuelve una discusión de opiniones en vez de una decisión basada en datos.

Autoevaluación

Pregunta 1 de 5

Según el ejemplo inicial, ¿cuál es el problema principal de un log como "error al procesar" escrito como texto libre?

Correcto: sin campos estructurados y consistentes, encontrar un evento específico entre miles de líneas parecidas se vuelve arqueología en vez de una consulta directa.
Pregunta 2 de 5

¿Qué expone específicamente Spring Boot Actuator que menciona esta página?

Correcto: Actuator viene con métricas estándar ya integradas (memoria, conexiones, latencia por endpoint) sin que el equipo tenga que instrumentar cada una manualmente.
Pregunta 3 de 5

Según la tabla de SLOs de esta página, ¿cuánto tiempo de falla al mes permite un SLO de 99.9% de disponibilidad?

Correcto: cada "nueve" adicional reduce el tiempo de falla permitido en un orden de magnitud — 99.9% equivale a aproximadamente 43 minutos de indisponibilidad tolerada por mes.
Pregunta 4 de 5

Según el callout sobre error budget, ¿qué decisión de equipo permite tomar un error budget explícito?

Correcto: el error budget convierte "¿deberíamos frenar features para estabilizar?" en una decisión basada en datos concretos, no en una discusión subjetiva.
Pregunta 5 de 5

Según el callout de "shift left" de esta página, ¿por qué invertir en logging estructurado antes de un incidente es más barato que hacerlo después?

Correcto: cuando ocurre un incidente serio (Módulo 8), reconstruir qué pasó exactamente depende completamente de la calidad de la evidencia que ya existía — no se puede instrumentar en retrospectiva un evento que ya ocurrió.
