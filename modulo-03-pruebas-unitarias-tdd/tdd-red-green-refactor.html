// el problema, otra vez

El bug que un test unitario hubiera atrapado en dos minutos

En el Módulo 1 viste la tabla de costo de un defecto según en qué etapa se detecta: 1× en diseño, hasta 1000× en producción. Este módulo es donde esa tabla deja de ser teoría. Un ejemplo real y aburrido — de los que sí pasan: una función que calcula el vuelto de una compra usa float en vez de un tipo decimal exacto. Con montos "normales" funciona. Con 0.10 + 0.20, el resultado no es 0.30 por cómo se representan los flotantes en binario, y un caso de cada varios miles se redondea mal.

Sin test unitario: nadie lo nota hasta que un cliente reporta un centavo de diferencia en su recibo, soporte investiga tres días, y el fix termina siendo una línea de código. Con un test unitario que verifica calcular_vuelto(1.00, 0.70) == 0.30, el error aparece en rojo apenas se escribe la función — antes de hacer commit, antes de abrir un PR, antes de que exista un solo usuario real.

Ese es el argumento completo de este módulo: los tests unitarios no prueban que "el código es bueno" en abstracto — prueban una afirmación concreta y barata de verificar, muchas veces por segundo, para siempre.

// vocabulario

¿Qué hace que un test sea "unitario"?

Un test unitario verifica la unidad de comportamiento más pequeña que tiene sentido probar por separado — normalmente una función o un método — de forma aislada del resto del sistema: sin base de datos real, sin red, sin sistema de archivos, sin reloj del sistema.

CaracterísticaTest unitarioLo que NO es
AlcanceUna función/método, en aislamiento.Varios módulos colaborando (eso es integración — Módulo 4).
Dependencias externasNinguna real: se reemplazan con dobles de prueba.Una base de datos real, una API externa real.
VelocidadMilisegundos. Una suite de miles corre en segundos.Segundos por test (señal de que no es realmente "unitario").
DeterminismoMismo resultado siempre, sin importar cuándo o dónde corre.Depende de la hora del día, del orden de otros tests, o de la red.
// checklist mental

Principios FIRST de un buen test unitario

Un acrónimo simple para evaluar si un test que acabas de escribir es realmente útil:

  • Fast (rápido). Si tu suite tarda minutos, dejarás de correrla seguido — y un test que no se corre no protege nada.
  • Independent (independiente). El resultado de un test no debe depender de que otro test haya corrido antes.
  • Repeatable (repetible). Mismo resultado en tu máquina, en la de tu compañero, y en el CI del Módulo 5.
  • Self-validating (auto-validante). El test dice pasó o falló solo — nadie lee un log a mano para decidir.
  • Timely (oportuno). Se escribe junto con el código, no "después, si sobra tiempo" — que casi nunca sobra.
La T de Timely es la que TDD fuerza por diseño: si escribes el test antes que el código, es matemáticamente imposible dejarlo para después.
// la práctica central de este módulo

El ciclo Red-Green-Refactor

Test-Driven Development (Kent Beck) invierte el orden habitual: en vez de escribir código y luego (quizás) un test, escribes primero un test que falla, y dejas que ese test te guíe hacia la implementación mínima que lo hace pasar.

PasoQué hacesPor qué importa
🔴 RedEscribes un test para una funcionalidad que todavía no existe. Lo corres y confirmas que falla.Si no lo ves fallar primero, no sabes si el test realmente prueba algo — un test que siempre pasa no protege nada.
🟢 GreenEscribes el código mínimo que hace pasar ese test. Feo está bien, rápido es la prioridad.Evita sobre-diseñar código para requisitos que todavía no están confirmados por un test.
🔵 RefactorCon el test en verde como red de seguridad, mejoras el diseño del código sin cambiar su comportamiento.Es el único momento seguro para limpiar: si rompes algo, el test se pone rojo de inmediato.
El ciclo se repite en minutos, no en horas. Cada vuelta agrega una sola afirmación nueva sobre el comportamiento del sistema. Al final de una kata de 30 minutos tienes tanto la implementación como su documentación ejecutable — los tests.
// aislar la unidad

Dobles de prueba: dummy, stub, fake, mock, spy

Para probar una unidad en aislamiento, sus dependencias (una base de datos, un servicio de pagos, el reloj del sistema) se reemplazan por dobles de prueba. No todos son lo mismo:

DobleQué haceEjemplo
DummySe pasa porque el código lo exige, nunca se usa realmente.Un objeto de configuración vacío pasado a un constructor.
StubDevuelve respuestas predefinidas, sin lógica.obtener_tasa_cambio() siempre devuelve 3.75 en el test.
FakeTiene una implementación real pero simplificada.Un repositorio en memoria en vez de una base de datos real.
MockVerifica que se le llamó de cierta forma (aserciones sobre interacción).Confirmar que enviar_email() se llamó exactamente una vez con el correo correcto.
SpyComo un fake, pero además registra cómo se le llamó, para inspeccionarlo después.Un logger falso que guarda todos los mensajes recibidos para verificarlos al final.

En la práctica, la mayoría de librerías (unittest.mock en Python, GoogleMock en C++, mocktail/mockito en Dart) usan la palabra "mock" para todos estos casos — la distinción de vocabulario importa para pensar con claridad, no para elegir el nombre de la clase.

// autoevaluación

Autoevaluación

Pregunta 1 de 5

Según el ejemplo de esta página, ¿en qué momento del ciclo de vida es más barato haber atrapado el bug de redondeo con float?

Correcto: mientras más temprano en el ciclo de vida (Módulo 1) se detecta el defecto, más barato es corregirlo. Un test unitario lo atrapa en el momento más temprano posible — antes de que exista un commit siquiera.
Pregunta 2 de 5

Un test tarda 4 segundos porque se conecta a una base de datos real. Según lo visto en esta página, ¿qué característica de un test unitario está violando?

Correcto: un test unitario real no toca dependencias externas reales como una base de datos — eso lo vuelve lento y ya no es realmente "unitario", sino una prueba de integración (Módulo 4).
Pregunta 3 de 5

En el ciclo Red-Green-Refactor, ¿por qué es importante ver el test fallar (Red) antes de escribir la implementación?

Correcto: si nunca ves el test fallar, no puedes distinguir "el test pasa porque el código es correcto" de "el test pasa siempre, sin importar qué haga el código" — un falso positivo silencioso.
Pregunta 4 de 5

Un test reemplaza el servicio de envío de emails con un objeto falso que registra que enviar() fue llamado exactamente una vez con el destinatario correcto. ¿Qué tipo de doble de prueba es principalmente?

Correcto: verificar cómo se le llamó (aserciones sobre la interacción) es la característica distintiva de un mock, a diferencia de un stub que solo devuelve datos predefinidos.
Pregunta 5 de 5

Durante el paso "Refactor" del ciclo TDD, ¿qué te da la confianza para mejorar el diseño del código sin miedo a romperlo?

Correcto: con el test verde, cualquier cambio que rompa el comportamiento existente se detecta de inmediato — eso es lo que hace seguro refactorizar justo en ese momento del ciclo.
