La kata: un validador de contraseñas

Vas a implementar la misma regla de negocio en Python, C++ y Flutter/Dart, siguiendo Red-Green-Refactor en cada uno. La regla, deliberadamente simple para que el foco esté en el proceso, no en el problema:

Una contraseña es válida si tiene al menos 8 caracteres, al menos un dígito y al menos una letra mayúscula.

Debajo se muestra el ciclo completo en Python (para ver las tres vueltas: Red, Green, Refactor), y luego el resultado equivalente — test + implementación final — en C++ y Flutter/Dart. El proceso para llegar ahí es idéntico en los tres: se muestra completo una vez para no repetir lo mismo tres veces.

// stack 1 de 3

Python — pytest

🔴 Red: se escribe el primer test, para la regla más simple (longitud), y se corre para verlo fallar.

test_validador.py
# todavía no existe validador.py — este test debe fallar con ImportError
from validador import es_valida

def test_rechaza_menor_a_8_caracteres():
    assert es_valida("Abc123") is False
bash
$ pytest -v
# ImportError: no module named 'validador' → Red confirmado

🟢 Green: la implementación mínima que hace pasar ese test — nada más.

validador.py
def es_valida(password):
    return len(password) >= 8

Se agregan las siguientes reglas, una por una, repitiendo Red-Green en cada vuelta:

test_validador.py — reglas agregadas
def test_rechaza_sin_digito():
    assert es_valida("Abcdefgh") is False

def test_rechaza_sin_mayuscula():
    assert es_valida("abc12345") is False

def test_acepta_password_valida():
    assert es_valida("Abcd1234") is True

🔵 Refactor: con las cuatro reglas en verde, se limpia la implementación usando expresiones regulares en vez de bucles manuales — el comportamiento no cambia, el diseño sí.

validador.py — final
import re

def es_valida(password: str) -> bool:
    if len(password) < 8:
        return False
    return bool(re.search(r"\d", password)) and bool(re.search(r"[A-Z]", password))
bash
$ pytest -v
# 4 passed — el refactor no rompió ninguna regla ya cubierta
// stack 2 de 3

C++ — GoogleTest

El ciclo es el mismo: se empieza por un test que falla al compilar (ni siquiera existe la función), luego la implementación mínima, y se agregan reglas una por una. Aquí se muestra el resultado tras completar las cuatro vueltas:

test_validador.cpp
#include <gtest/gtest.h>
#include "validador.h"

TEST(ValidadorPassword, RechazaMenorA8Caracteres) {
    EXPECT_FALSE(es_valida("Abc123"));
}

TEST(ValidadorPassword, RechazaSinDigito) {
    EXPECT_FALSE(es_valida("Abcdefgh"));
}

TEST(ValidadorPassword, RechazaSinMayuscula) {
    EXPECT_FALSE(es_valida("abc12345"));
}

TEST(ValidadorPassword, AceptaPasswordValida) {
    EXPECT_TRUE(es_valida("Abcd1234"));
}
validador.cpp — final (tras refactor)
#include "validador.h"
#include <regex>

bool es_valida(const std::string& password) {
    if (password.length() < 8) return false;
    return std::regex_search(password, std::regex("\\d")) &&
           std::regex_search(password, std::regex("[A-Z]"));
}
bash — CMake + CTest
$ cmake -B build && cmake --build build
$ ctest --test-dir build --output-on-failure
# 4/4 tests pasando
Lo que solo ves en C++: el "Red" inicial aquí es un error de compilación (validador.h no existe todavía), no solo una aserción fallida. Eso agrega un paso extra a cada vuelta del ciclo — declarar la firma en el header antes de poder ver el test correr — y es una de las razones por las que TDD "se siente" más lento en C++ que en Python.
// stack 3 de 3

Flutter/Dart — flutter_test

Igual proceso: cuatro vueltas de Red-Green, mismas reglas, ahora en Dart puro (esta lógica no depende de ningún widget, así que ni siquiera hace falta WidgetTester — es un test unitario normal dentro de un proyecto Flutter).

test/validador_test.dart
import 'package:flutter_test/flutter_test.dart';
import 'package:mi_app/validador.dart';

void main() {
  test('rechaza contraseñas menores a 8 caracteres', () {
    expect(esValida('Abc123'), isFalse);
  });

  test('rechaza contraseñas sin dígito', () {
    expect(esValida('Abcdefgh'), isFalse);
  });

  test('rechaza contraseñas sin mayúscula', () {
    expect(esValida('abc12345'), isFalse);
  });

  test('acepta una contraseña válida', () {
    expect(esValida('Abcd1234'), isTrue);
  });
}
lib/validador.dart — final (tras refactor)
bool esValida(String password) {
  if (password.length < 8) return false;
  final tieneDigito = RegExp(r'\d').hasMatch(password);
  final tieneMayuscula = RegExp(r'[A-Z]').hasMatch(password);
  return tieneDigito && tieneMayuscula;
}
bash
$ flutter test
# 00:01 +4: All tests passed!
// el punto de hacerlo tres veces

Lo que cambia y lo que no cambia entre stacks

Python (pytest)C++ (GoogleTest)Flutter/Dart (flutter_test)
El ciclo Red-Green-RefactorIdéntico en los tres — esa es la parte que no cambia nunca.
Qué significa "Red"Aserción fallida o ImportErrorPuede ser error de compilación, no solo aserciónAserción fallida (interpretado, sin paso de compilación)
Velocidad del cicloMuy rápida (interpretado)Más lenta — cada vuelta puede requerir recompilarRápida con hot reload en desarrollo
Riesgo dominanteTipado dinámico: un error de tipo solo aparece en tiempo de ejecuciónGestión manual de memoria y punteros — un test puede pasar y aun así haber undefined behavior (Módulo 7)Acoplar la lógica de negocio a un widget en vez de aislarla (dificulta el test unitario)
Corredor de testspytestctest (vía CMake)flutter test

El objetivo de repetir la kata tres veces no es memorizar sintaxis — es notar que el proceso de diseño guiado por tests es transferible entre lenguajes, mientras que los riesgos específicos de cada ecosistema (tipado dinámico, memoria manual, acoplamiento a UI) requieren atención distinta en cada uno.

Pregunta 1 de 5

En la kata de esta página, ¿cuál fue la primera regla que se implementó, y por qué se empezó por ahí?

Correcto: TDD avanza en pasos pequeños. Empezar por la regla más simple permite completar una vuelta completa de Red-Green-Refactor rápido, en vez de intentar resolver las cuatro reglas de una sola vez.
Pregunta 2 de 5

Según la tabla de comparación, ¿qué hace que el paso "Red" en C++ sea distinto al de Python y Flutter/Dart?

Correcto: como validador.h no existe aún, el primer intento de compilar el test falla directamente — un paso adicional frente a Python o Dart, que son interpretados y solo fallarían en la aserción o el import.
Pregunta 3 de 5

¿Qué cambió exactamente durante el paso "Refactor" en la versión de Python de la kata?

Correcto: refactorizar significa mejorar el diseño interno sin alterar el comportamiento externo. Los cuatro tests existentes siguieron pasando exactamente igual después del cambio.
Pregunta 4 de 5

¿Por qué el test de Flutter/Dart de esta página no necesitó usar WidgetTester ni montar ningún widget?

Correcto: al mantener la lógica de validación separada de la UI, se puede probar como una función Dart pura y rápida — sin necesidad de infraestructura de widgets, que sí se usa para pruebas de UI (Módulo 4).
Pregunta 5 de 5

Según la tabla de comparación, ¿cuál es el riesgo dominante mencionado específicamente para el stack de C++ que no aparece igual en Python ni Flutter/Dart?

Correcto: un test en verde en C++ no garantiza ausencia de undefined behavior (memoria mal manejada, punteros colgantes) — ese riesgo se ataca con sanitizers y Valgrind en el Módulo 7, no con tests unitarios solos.
