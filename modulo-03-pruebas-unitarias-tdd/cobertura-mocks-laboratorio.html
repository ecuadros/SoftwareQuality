Cobertura de código: qué mide y qué no mide

La cobertura de código mide qué porcentaje de tu código se ejecutó al correr la suite de tests. Es útil como red de seguridad ("¿hay código sin ningún test que lo toque?"), pero es una métrica de ejecución, no de corrección.

TipoQué cuentaLimitación
Cobertura de líneasQué porcentaje de líneas se ejecutó al menos una vez.Una línea "cubierta" puede tener una aserción débil o ninguna — solo dice que se ejecutó, no que se verificó su resultado.
Cobertura de ramasQué porcentaje de caminos posibles (if/else, condiciones) se ejecutó.Más estricta que la de líneas, pero sigue sin garantizar que las aserciones sean correctas.
El ejemplo clásico: assert es_valida("Abcd1234") is not None "cubre" la línea de la función, pero no verifica que el resultado sea True específicamente. 100% de cobertura con aserciones así de débiles da una falsa sensación de seguridad. Persigue cobertura como señal de código sin ningún test, no como objetivo final en sí mismo — la técnica más rigurosa para medir la calidad real de tus aserciones (mutation testing) se menciona en el Módulo 6.

Herramientas de cobertura por stack

bash — Python (coverage.py)
$ coverage run -m pytest
$ coverage report -m
# Name             Stmts   Miss  Cover   Missing
# validador.py         6      0   100%
$ coverage html   # genera htmlcov/index.html navegable
bash — C++ (gcov + lcov)
# compilar con instrumentación de cobertura
$ cmake -B build -DCMAKE_CXX_FLAGS="--coverage"
$ cmake --build build
$ ctest --test-dir build
$ lcov --capture --directory build --output-file coverage.info
$ genhtml coverage.info --output-directory coverage-html
bash — Flutter/Dart
$ flutter test --coverage
# genera coverage/lcov.info
$ genhtml coverage/lcov.info -o coverage/html
bash — Java/Spring Boot (JaCoCo vía Maven)
$ mvn test jacoco:report
# genera target/site/jacoco/index.html navegable

Python, C++ y Flutter/Dart terminan en el mismo formato lcov reportable como HTML — conveniente porque en el Módulo 5 vas a subir ese mismo reporte como artefacto de CI. JaCoCo usa su propio formato nativo (XML/HTML) en vez de lcov, pero en el Módulo 6 vas a integrar cualquiera de los dos formatos a SonarCloud como parte del quality gate — ambos son de primera clase ahí, no hace falta convertir uno al otro.

Mockear una dependencia externa

Supón que el validador de contraseñas ahora debe rechazar contraseñas que aparezcan en una lista de contraseñas filtradas, consultada contra un servicio externo. No quieres que tu test unitario dependa de internet ni de que ese servicio esté arriba — lo reemplazas con un mock.

test_validador.py — con unittest.mock
from unittest.mock import Mock
from validador import es_valida

def test_rechaza_password_filtrada():
    servicio_filtradas = Mock()
    servicio_filtradas.esta_filtrada.return_value = True

    resultado = es_valida("Abcd1234", servicio_filtradas)

    assert resultado is False
    servicio_filtradas.esta_filtrada.assert_called_once_with("Abcd1234")

El equivalente conceptual existe en los otros tres stacks, con librerías dedicadas — no se repite el código completo aquí porque la idea (reemplazar la dependencia real por un doble controlado) es exactamente la misma que en el ejemplo de Python:

StackLibrería de mockingSintaxis equivalente
Pythonunittest.mock / pytest-mockmock.esta_filtrada.return_value = True
C++GoogleMock (parte de GoogleTest)EXPECT_CALL(mock, esta_filtrada("Abcd1234")).WillOnce(Return(true));
Flutter/Dartmocktail (o mockito)when(() => mock.estaFiltrada(any())).thenReturn(true);
Java/Spring BootMockitowhen(servicioFiltradas.estaFiltrada("Abcd1234")).thenReturn(true);
En Spring Boot, @MockBean va un paso más allá que Mockito puro: reemplaza el bean real dentro del contexto de inyección de dependencias de Spring por el mock, útil cuando la clase bajo prueba recibe su dependencia vía @Autowired en vez de por parámetro directo.

Autoevaluación

Pregunta 1 de 6

Un test hace assert resultado is not None sobre una función que debería devolver exactamente True. Aunque la línea queda "cubierta" al 100%, ¿qué problema tiene esta aserción según lo visto en esta página?

Correcto: la cobertura mide ejecución, no corrección de las aserciones. Un 100% con aserciones débiles da una falsa sensación de seguridad — exactamente la advertencia central de esta página.
Pregunta 2 de 6

¿Qué formato de reporte comparten coverage.py, gcov/lcov y flutter test --coverage, a diferencia de JaCoCo en Java/Spring Boot?

Correcto: esas tres terminan en lcov.info (o equivalente); JaCoCo usa su propio formato nativo en vez de lcov. SonarCloud (Módulo 6) entiende ambos formatos de primera clase.
Pregunta 3 de 6

En el ejemplo de mockear el servicio de contraseñas filtradas, ¿por qué se usa un mock en vez de llamar al servicio real durante el test?

Correcto: mantiene el test unitario rápido, aislado y determinista (principios FIRST, página anterior) — probar contra el servicio real de verdad es responsabilidad de las pruebas de integración (Módulo 4).
Pregunta 4 de 6

Según el checklist de laboratorio de esta página, ¿qué evidencia concreta en el historial de Git demuestra que sí se siguió TDD y no solo se escribió el código y los tests al final?

Correcto: solo el historial de commits separando red de green (y luego refactor) demuestra el proceso real — el código final se ve idéntico haya o no haya seguido TDD.
Pregunta 5 de 6

¿Qué mide de forma más estricta la "cobertura de ramas" en comparación con la "cobertura de líneas"?

Correcto: una línea con un if/else puede contar como "cubierta" con solo probar una de las dos ramas; la cobertura de ramas exige haber ejercitado ambos caminos posibles.
Pregunta 6 de 6

En un test de Spring Boot, la clase bajo prueba recibe el servicio de contraseñas filtradas vía @Autowired en vez de como parámetro. ¿Qué anotación de Mockito/Spring reemplaza ese bean real por un mock dentro del contexto de inyección de dependencias?

Correcto: @MockBean es específico de Spring Boot Test — a diferencia de un mock de Mockito puro (que se pasa a mano), reemplaza el bean real dentro del contexto de Spring, útil cuando la dependencia se inyecta automáticamente en vez de recibirse por parámetro.
