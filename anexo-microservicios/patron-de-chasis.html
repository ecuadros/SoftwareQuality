// el problema

N servicios, N formas distintas de resolver lo mismo

Un equipo construye salud-service siguiendo todo lo de este curso: pipeline de CI (Módulo 5), logging estructurado (Módulo 7), análisis estático (Módulo 6), dependency scanning (Módulo 7). Meses después, otro equipo dentro de la misma organización empieza educacion-service desde cero — y sin darse cuenta, configura el logging con otro formato de campos, otro umbral de cobertura, otra versión del linter. Cuando llega agricultura-service, ya hay tres formas ligeramente distintas de hacer exactamente lo mismo.

El costo se multiplica por cada servicio nuevo. Ninguna de las tres decisiones fue "incorrecta" por separado — pero ahora quien opera el sistema completo tiene que aprender tres formatos de log distintos para investigar un incidente que cruza los tres servicios (el problema exacto de trazabilidad distribuida del Módulo 7), y cada mejora de seguridad o de calidad hay que aplicarla tres veces, por separado, con tres resultados posiblemente distintos.

El problema no es tener varios servicios — es no tener una base común explícita para las decisiones que no deberían variar de servicio a servicio.

// el nombre viene de un auto, literalmente

El patrón de Chasis

El Microservice Chassis (Chris Richardson, Microservices Patterns) toma prestado el nombre de la industria automotriz: un chasis es el armazón estructural sobre el que se monta cualquier modelo de auto — un sedán, una camioneta, un auto deportivo pueden tener carrocerías completamente distintas, pero comparten el mismo chasis con el motor, la suspensión, el sistema eléctrico y los frenos ya resueltos.

Un chasis de microservicio es exactamente eso: una plantilla base — un proyecto starter, una librería compartida, un parent POM — que resuelve de una sola vez todas las decisiones de calidad que no deberían depender de qué hace el servicio. Cada servicio nuevo hereda el chasis y solo agrega lo que lo hace único: su lógica de dominio.

Nada de esto es una herramienta nueva que no hayas visto — es un empaquetado de decisiones que ya tomaste en los Módulos 3 a 7, para no volver a tomarlas manualmente cada vez que nace un servicio nuevo.

Anatomía de un chasis: lo que ya construiste, empaquetado

Elemento del chasisDe dónde salePor qué NO debería decidirse por servicio
Framework de testing + umbral de coberturaMódulo 3Si cada servicio define su propio umbral, "calidad suficiente" deja de significar algo comparable entre equipos.
Pipeline de CI/CD con quality gatesMódulo 5Copiar y pegar el YAML en cada repo nuevo garantiza que diverjan con el tiempo — un chasis lo centraliza en una action reusable o un template de workflow.
Análisis estático y dependency scanning preconfiguradosMódulos 6-7Las mismas reglas de Checkstyle/PMD/SpotBugs y el mismo escáner de CVEs deberían aplicar a todo el fleet, no a criterio de cada equipo.
Logging estructurado con el mismo esquema de camposMódulo 7Sin un esquema común, correlacionar logs entre servicios (trace ID incluido) se vuelve imposible.
Health checks y métricas (Actuator)Módulo 7El orquestador (Kubernetes, un load balancer) necesita preguntar "¿estás sano?" de la misma forma a cualquier servicio del fleet.
Circuit breaker con configuración por defecto razonableMódulo 7Un servicio que olvida configurar resiliencia hacia sus dependencias arriesga una falla en cascada que afecta a todos los demás.
Nota el patrón: todas las filas son cosas que un servicio necesita para ser operable de forma consistente junto a otros — ninguna tiene que ver con si el servicio gestiona citas médicas, matrículas escolares o cosechas. Esa es exactamente la línea que separa "chasis" de "lógica de negocio".

El mapa de Lego: salud, educación y agricultura

Piensa en un chasis de microservicio como la placa base de Lego: todas las piezas que se construyen encima pueden ser completamente distintas — una nave espacial, un castillo, un auto — pero todas se conectan al mismo patrón de conectores. Nadie rediseña la placa base cada vez que arma algo nuevo.

salud-serviceeducacion-serviceagricultura-service
Entidad de dominioCita médicaMatrículaCosecha
Regla de negocio únicaUn médico no puede tener dos citas superpuestasUn estudiante no puede matricularse en cursos con horario cruzadoUna parcela no puede cosecharse dos veces en la misma temporada
Chasis compartidoIdéntico en los tres: mismo pipeline, mismo formato de logs, mismo health check, mismo circuit breaker por defecto.

Tres dominios sin absolutamente nada en común a nivel de negocio — y aun así, quien opera el sistema completo puede investigar un incidente en cualquiera de los tres de la misma forma, porque el chasis nunca varió. Eso es lo que hace posible que "salud", "educación" y "agricultura" convivan en el mismo fleet de servicios sin que cada uno sea una isla operativa distinta.

Autoevaluación

Pregunta 1 de 5

En el ejemplo inicial, ¿cuál fue exactamente el problema entre salud-service, educacion-service y agricultura-service?

Correcto: el problema no fue la calidad individual de cada decisión, sino la falta de una base compartida — lo que hace que investigar o mejorar el sistema completo cueste tres veces más.
Pregunta 2 de 5

¿De dónde viene el nombre "chasis" para este patrón?

Correcto: la metáfora es literal — igual que un sedán y una camioneta comparten motor, suspensión y sistema eléctrico bajo carrocerías distintas, los microservicios comparten un chasis de decisiones de calidad bajo lógicas de negocio distintas.
Pregunta 3 de 5

Según la tabla de anatomía del chasis, ¿por qué el umbral de cobertura de tests NO debería decidirse por separado en cada servicio?

Correcto: el chasis centraliza justamente las decisiones que deben ser consistentes para que la organización entera hable el mismo idioma de calidad, sin importar quién construyó cada servicio.
Pregunta 4 de 5

Según el callout de esta página, ¿qué línea separa lo que va DENTRO del chasis de lo que NO va?

Correcto: health checks, logging, CI, circuit breakers son necesarios sin importar si el servicio gestiona citas médicas o cosechas — esa independencia del dominio es justo lo que los hace parte del chasis y no de la lógica de negocio.
Pregunta 5 de 5

En la metáfora de Lego de esta página, ¿qué representa la "placa base" en el contexto de microservicios?

Correcto: la placa base es fija y compartida (el chasis); lo que se construye encima —la lógica de negocio de salud, educación o agricultura— es lo que varía libremente, como las piezas de Lego.
