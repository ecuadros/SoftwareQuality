El chasis como parent POM

En Maven, un parent POM es un archivo del que otros proyectos heredan configuración — versiones de dependencias, plugins de build, propiedades. Es el lugar natural para materializar el chasis: cada elemento de la tabla de la página anterior se declara una sola vez aquí.

acme-chasis/pom.xml
<project>
  <groupId>com.acme</groupId>
  <artifactId>acme-chasis</artifactId>
  <version>1.4.0</version>
  <packaging>pom</packaging>

  <dependencyManagement>
    <dependencies>
      <!-- Módulo 7: health checks, métricas -->
      <dependency><groupId>org.springframework.boot</groupId><artifactId>spring-boot-starter-actuator</artifactId></dependency>
      <!-- Módulo 7: circuit breaker -->
      <dependency><groupId>io.github.resilience4j</groupId><artifactId>resilience4j-spring-boot3</artifactId></dependency>
      <!-- Módulo 7: tracing distribuido -->
      <dependency><groupId>io.micrometer</groupId><artifactId>micrometer-tracing-bridge-otel</artifactId></dependency>
      <!-- Módulo 7: logging estructurado -->
      <dependency><groupId>net.logstash.logback</groupId><artifactId>logstash-logback-encoder</artifactId></dependency>
      <!-- Módulo 4: pruebas de integración con dependencias reales -->
      <dependency><groupId>org.testcontainers</groupId><artifactId>junit-jupiter</artifactId></dependency>
    </dependencies>
  </dependencyManagement>

  <build>
    <pluginManagement>
      <plugins>
        <!-- Módulo 3: cobertura mínima obligatoria -->
        <plugin><artifactId>jacoco-maven-plugin</artifactId>
          <configuration><rules><rule><limits><limit><minimum>0.80</minimum></limit></limits></rule></rules></configuration>
        </plugin>
        <!-- Módulo 6: mismas reglas de análisis estático para todo el fleet -->
        <plugin><artifactId>checkstyle-maven-plugin</artifactId></plugin>
        <plugin><artifactId>pmd-maven-plugin</artifactId></plugin>
        <plugin><groupId>com.github.spotbugs</groupId><artifactId>spotbugs-maven-plugin</artifactId></plugin>
        <!-- Módulo 7: mismo escáner de CVEs para todo el fleet -->
        <plugin><groupId>org.owasp</groupId><artifactId>dependency-check-maven</artifactId></plugin>
      </plugins>
    </pluginManagement>
  </build>
</project>
Nota lo que no hay en este archivo: ninguna mención a citas médicas, matrículas o cosechas. Todo lo que hay aquí es exactamente lo que cualquier servicio del fleet necesita, sin importar qué hace — la línea que separaste en la página anterior, ahora en código.

Configuración base compartida

El chasis no es solo dependencias — también fija la configuración por defecto que todo servicio hereda, para que investigar cualquiera de ellos se sienta igual:

application-chasis.yml — incluido por todos los servicios
management:
  endpoints:
    web:
      exposure:
        include: health, metrics, prometheus   # mismo contrato de observabilidad, Módulo 7

logging:
  structured:
    format: ecs   # mismo esquema de campos JSON en todos los servicios

resilience4j:
  circuitbreaker:
    configs:
      default:
        failure-rate-threshold: 50   # mismo umbral por defecto, Módulo 7
        wait-duration-in-open-state: 10s
// la placa base, con piezas distintas encima

Tres servicios, un mismo chasis

Cada servicio de dominio declara el chasis como <parent> y agrega únicamente lo que lo hace único — su entidad de dominio y las dependencias específicas que necesita, nada de lo que ya resolvió el chasis.

salud-service/pom.xml
<parent>
  <groupId>com.acme</groupId>
  <artifactId>acme-chasis</artifactId>
  <version>1.4.0</version>
</parent>
<artifactId>salud-service</artifactId>
salud-service/src/main/java/Cita.java — lo único de este servicio
public record Cita(String paciente, String medico, LocalDateTime fecha) {
    public boolean seSuperponeCon(Cita otra) {
        return this.medico().equals(otra.medico()) && this.fecha().equals(otra.fecha());
    }
}
educacion-service/src/main/java/Matricula.java — lo único de este servicio
public record Matricula(String estudiante, String curso, String periodo, Horario horario) {
    public boolean chocaConHorarioDe(Matricula otra) {
        return this.periodo().equals(otra.periodo()) && this.horario().seSolapaCon(otra.horario());
    }
}
agricultura-service/src/main/java/Cosecha.java — lo único de este servicio
public record Cosecha(String parcela, String cultivo, String temporada, double kilogramos) {
    public boolean yaCosechadaEnTemporada(String parcela, String temporada, List<Cosecha> historial) {
        return historial.stream().anyMatch(c -> c.parcela().equals(parcela) && c.temporada().equals(temporada));
    }
}
Qué comparten los tres (el chasis)Qué es único de cada uno (el dominio)
Umbral de cobertura, linters, escáner de CVEsSus propias entidades: Cita, Matricula, Cosecha
Formato de logs y propagación de trace IDSus propias reglas de negocio y validaciones
Endpoints de health check y métricasSu propio modelo de datos en MongoDB
Configuración por defecto del circuit breakerSus propios endpoints REST específicos del dominio
Cuando el equipo de plataforma mejora el chasis — sube el umbral de cobertura, agrega una regla nueva de SpotBugs, actualiza el formato de tracing — los tres servicios lo heredan con solo actualizar una versión en su <parent>, no con tres PRs manuales idénticos.

¿Y en Python, C++ o Flutter/Dart?

El parent POM es la forma más directa de mostrar un chasis porque Maven lo resuelve de forma nativa — pero el patrón no depende de Maven ni de Java. El mismo principio se materializa distinto en cada ecosistema:

StackCómo se vería el chasis
PythonUn paquete interno instalable (acme-chasis en un índice privado) con middleware de logging/tracing para FastAPI, configuración de pytest-cov compartida, y un Dockerfile base.
C++Una plantilla de CMake compartida (acme_chasis.cmake) que fija flags de sanitizers, integración con GoogleTest y el target de cobertura, incluida vía include() en cada servicio.
Flutter/DartUn paquete pub interno con analysis_options.yaml base, un cliente HTTP con propagación de trace ID incluida, y widgets de manejo de errores compartidos.

Pregunta 1 de 5

En el ejemplo de acme-chasis/pom.xml, ¿qué tienen en común todas las dependencias y plugins declarados ahí?

Correcto: esa ausencia deliberada de lógica de negocio es justo la línea que separa "chasis" de "dominio" que se estableció en la página anterior.
Pregunta 2 de 5

Cuando el equipo de plataforma mejora el chasis (por ejemplo, sube el umbral mínimo de cobertura), ¿qué deben hacer salud-service, educacion-service y agricultura-service para adoptar el cambio?

Correcto: esa es la ventaja concreta del chasis — una sola actualización de versión propaga la mejora a todos los servicios que lo heredan, en vez de requerir un PR manual idéntico en cada repo.
Pregunta 3 de 5

Según la tabla de "qué comparten / qué es único", ¿en qué columna cae la clase Cosecha de agricultura-service?

Correcto: las entidades de dominio (Cita, Matricula, Cosecha) son exactamente lo que cada servicio agrega por encima del chasis — la parte que sí varía.
Pregunta 4 de 5

Según la tabla de otros stacks, ¿cómo se vería un chasis en un proyecto Flutter/Dart, a diferencia del parent POM de Java?

Correcto: el mecanismo concreto cambia según el ecosistema (paquete pub en vez de parent POM), pero el principio —empaquetar las decisiones transversales una sola vez— es el mismo patrón.
