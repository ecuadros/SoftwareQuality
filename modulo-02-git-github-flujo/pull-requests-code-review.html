Anatomía de un buen Pull Request

Un PR es una solicitud de atención de otro ser humano. La calidad del PR determina qué tan rápido y qué tan bien te van a revisar.

  • Pequeño. Un PR de +50 líneas se revisa peor que uno de +500 — no porque el revisor no pueda leer tanto, sino porque la atención humana se degrada después de cierto punto y empieza a aprobar "de confianza". Divide features grandes en varios PRs.
  • Una sola cosa. No mezcles una corrección de bug con un refactor "ya que estaba ahí". Dificulta el review y el git bisect futuro.
  • Descripción con contexto, no solo el qué. La plantilla del Módulo 1 ya te obliga a esto: qué cambia, por qué, cómo se probó.
  • Se auto-revisa primero. Lee tu propio diff en GitHub antes de pedir revisión — encontrarás la mitad de los comentarios que recibirías, sin gastar el tiempo de nadie más.

Cómo revisar código de otra persona

Revisar código es una habilidad distinta a escribirlo. El objetivo no es demostrar que sabes más — es proteger la calidad del repo compartido sin frenar al equipo innecesariamente.

Sí frena el mergeNo debería frenar el merge
El código no hace lo que dice que hace (correctitud).Preferencias de estilo que un linter debería atrapar (Módulo 6) — coméntalo, pero como sugerencia, no bloqueo.
Falta un caso de prueba obvio para la lógica nueva."Yo lo hubiera escrito distinto" sin una razón concreta de mantenibilidad o corrección.
Introduce un riesgo de seguridad (input sin validar, secreto hardcodeado).Nombres de variable que no son los que tú elegirías, si son claros igual.
Rompe una convención de arquitectura acordada por el equipo.Micro-optimizaciones sin evidencia de que el rendimiento importa ahí.
Checklist mental del revisor
  • ¿Entiendo qué problema resuelve este cambio con solo leer la descripción?
  • ¿El código hace lo que dice? ¿Hay un caso límite obvio sin cubrir?
  • ¿Hay tests para la lógica nueva o modificada?
  • ¿Introduce algo que comprometa seguridad, datos sensibles o rendimiento crítico?
  • ¿Podría entender este código en seis meses sin preguntarle al autor?
Sesgo común a evitar: aprobar sin leer de verdad porque "confío en quien lo escribió". Un PR aprobado sin revisión real no es una red de seguridad — es teatro de proceso. Si tu repo exige aprobación (Módulo 1), que sea porque de verdad alguien leyó el diff.

CODEOWNERS: revisores automáticos

En vez de acordarte de pedir revisión a la persona correcta cada vez, un archivo CODEOWNERS hace que GitHub la asigne sola según qué archivos toca el PR — y, combinado con Require review from Code Owners en branch protection, hace la revisión de esa persona obligatoria, no opcional.

.github/CODEOWNERS
# Dueño por defecto de todo el repo
*                       @tu-usuario

# La persona/equipo que revisa specificamente la parte de CI
/.github/workflows/     @tu-usuario

# Si trabajas en equipo, cada quien puede ser owner de su módulo
/src/pagos/             @companera-de-equipo
/src/inventario/        @tu-usuario

En un proyecto solo, CODEOWNERS parece innecesario — pero déjalo configurado desde ya: en cuanto trabajes en pareja para el ejercicio de abajo, o en el proyecto final en equipo, ya está listo.

Autoevaluación

Un revisor comenta: "Yo habría usado un for en vez de una list comprehension, pero ambos funcionan igual de bien y son igual de legibles." ¿Debería este comentario bloquear el merge?

Correcto: si ambas formas son igual de correctas y legibles, es una preferencia personal. Bloquear merges por esto desgasta la relación de equipo y hace que la gente deje de pedir revisión a tiempo. Guarda el bloqueo para correctitud, tests, seguridad y mantenibilidad real.
