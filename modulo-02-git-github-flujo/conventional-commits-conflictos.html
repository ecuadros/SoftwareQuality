Conventional Commits

Conventional Commits es una convención simple para el mensaje de commit: tipo(alcance): descripción. No es burocracia — es lo que en el Módulo 5 te va a permitir generar un changelog y decidir la siguiente versión semántica automáticamente, sin que nadie lo escriba a mano.

TipoCuándo usarloEjemplo
featNueva funcionalidad para el usuario.feat(pagos): agrega validación de tarjeta
fixCorrección de un bug.fix(inventario): corrige redondeo de stock negativo
testAgregar o corregir tests, sin tocar código de producción.test(pagos): cubre caso de tarjeta expirada
refactorCambio interno sin alterar comportamiento observable.refactor(pagos): extrae validación a función pura
docsSolo documentación.docs: agrega guía de instalación
choreMantenimiento (dependencias, configuración) sin impacto en el código fuente.chore: actualiza pytest a 8.x
ciCambios al pipeline de integración continua.ci: agrega job de cobertura
Regla práctica: si tu mensaje de commit necesita un "y" para describirlo ("agrega validación y corrige un bug"), probablemente son dos commits, no uno. Un commit debería poder revertirse solo, sin arrastrar un cambio no relacionado.

Anatomía de un conflicto de merge

Un conflicto ocurre cuando dos ramas modificaron la misma línea (o líneas adyacentes) de un archivo de forma distinta, y Git no puede decidir cuál versión es la correcta — con razón, porque es una decisión que solo tú puedes tomar.

bash — al fusionar aparece esto
$ git merge feature/descuento-vip
Auto-merging src/pagos.py
CONFLICT (content): Merge conflict in src/pagos.py
Automatic merge failed; fix conflicts and then commit the result.
src/pagos.py — marcadores de conflicto
def calcular_descuento(monto):
<<<<<<< HEAD
    return monto * 0.10  # tu rama: 10% fijo
=======
    return monto * 0.15 if monto > 100 else monto * 0.05  # su rama: descuento variable
>>>>>>> feature/descuento-vip

Los pasos para resolverlo, siempre iguales:

  1. Abre el archivo y decide qué versión (o combinación de ambas) es la correcta — hablando con el autor de la otra rama si hace falta, no adivinando.
  2. Borra los tres marcadores (<<<<<<<, =======, >>>>>>>) dejando solo el código final.
  3. git add archivo-resuelto.py — le dice a Git que ya decidiste.
  4. git commit (sin -m, Git ya prepara un mensaje de merge) o git rebase --continue si estabas en un rebase.
  5. Corre los tests localmente antes de hacer push — un conflicto resuelto sintácticamente puede seguir estando semánticamente mal.

Laboratorio: provoca un conflicto real y resuélvelo

Practica en tu propio repo, sin depender de nadie más, antes de que te ocurra "en caliente" con un compañero.

bash
# 1. Desde main, crea dos ramas que modificarán la misma línea
git checkout main
git checkout -b feature/rama-a
# edita una línea de un archivo existente, por ejemplo cambia un mensaje
git commit -am "feat: cambia mensaje de bienvenida (versión A)"
git checkout main
git checkout -b feature/rama-b
# edita esa MISMA línea de forma distinta
git commit -am "feat: cambia mensaje de bienvenida (versión B)"

# 2. Fusiona la primera sin problema
git checkout main
git merge feature/rama-a

# 3. Al fusionar la segunda, Git debería reportar CONFLICT
git merge feature/rama-b
Al resolverlo, confirma que hiciste esto

Autoevaluación

Pregunta 1 de 5

Ves este marcador en un archivo tras un git merge: <<<<<<< HEAD. ¿Qué representa el bloque de código que viene justo después de esa línea, antes del =======?

Correcto: todo lo que está entre <<<<<<< HEAD y ======= es tu rama actual. Lo que está entre ======= y >>>>>>> nombre-rama es la rama que estás fusionando. Git nunca decide "cuál es la correcta" por ti — solo te muestra ambas para que elijas.
Pregunta 2 de 5

¿Qué tipo de Conventional Commit usarías para un cambio que agrega tests nuevos sin tocar código de producción?

Correcto: test es exactamente para eso — agregar o corregir tests sin alterar el comportamiento del código de producción.
Pregunta 3 de 5

Un commit dice: "agrega validación de tarjeta y corrige un bug de redondeo". Según la regla práctica vista en esta página, ¿qué problema tiene?

Correcto: si el mensaje necesita un "y" para describirlo, son dos cambios. Un commit debería poder revertirse solo, sin arrastrar algo no relacionado.
Pregunta 4 de 5

Al resolver un conflicto de merge, ¿qué comando le indica a Git que ya decidiste cuál versión del código es la correcta?

Correcto: después de eliminar los marcadores y dejar el código final, git add marca ese archivo como resuelto. Recién entonces git commit completa el merge.
Pregunta 5 de 5

¿Por qué se recomienda correr los tests localmente después de resolver un conflicto, antes de hacer push?

Correcto: elegir "la versión correcta" de un conflicto no garantiza que el programa siga funcionando — solo los tests confirman que el resultado combinado realmente funciona.
