// el problema

El problema que resuelve una estrategia de ramas

Con un solo desarrollador, trabajar directo sobre main "funciona". En cuanto hay dos personas tocando el mismo repo, aparecen preguntas que sin una estrategia explícita cada quien responde distinto: ¿cuándo integro mi trabajo al de los demás? ¿Puedo desplegar si mi rama no está fusionada? ¿Qué pasa si mi feature tarda dos semanas en terminar?

Una estrategia de ramas es simplemente un acuerdo de equipo sobre esas preguntas, aplicado además por herramienta (branch protection, Módulo 1) en vez de solo por memoria.

// la que vas a usar en este curso

GitHub Flow

Es el flujo más simple que funciona bien en equipos pequeños y con despliegue continuo — el que vas a usar en tu proyecto de este curso. Reglas:

  1. main siempre está en estado desplegable. Nunca queda roto.
  2. Para cualquier cambio, se crea una rama con nombre descriptivo desde main: feature/validacion-pago, fix/redondeo-centavos.
  3. Se hacen commits en esa rama y se abre un Pull Request apenas hay algo que discutir — no hace falta esperar a terminar.
  4. Se revisa (Módulo 2, siguiente página), se corrige, y cuando el CI pasa (Módulo 5) y hay aprobación, se fusiona a main.
  5. Se elimina la rama. main se despliega.
La clave operativa: ramas de vida corta (idealmente menos de 2-3 días). Cuanto más vive una rama sin fusionarse, más diverge de main y más doloroso es el merge — es la causa número uno de los conflictos que vas a resolver más adelante en este módulo.
// la versión de alta frecuencia

Trunk-Based Development

Es una versión aún más agresiva: los desarrolladores integran a main (el "tronco", trunk) al menos una vez al día, con ramas que viven horas, no días. Funcionalidad incompleta se esconde detrás de feature flags en vez de vivir aislada en una rama larga.

En GitHub FlowEn Trunk-Based
La feature incompleta vive en su propia rama hasta terminar.La feature incompleta se integra a main ya, pero apagada por un feature flag.
El PR puede tardar días en fusionarse.El PR se fusiona en horas; cambios grandes se parten en varios PRs pequeños.
Riesgo: ramas que divergen y generan conflictos grandes.Riesgo: requiere más disciplina de feature flags y tests, o main se ensucia rápido.

Empresas con despliegues múltiples por día (piensa en equipos grandes de producto) suelen usar Trunk-Based porque minimiza el "big bang" de integración. Para un proyecto de curso o un equipo pequeño, GitHub Flow da el mismo beneficio con menos ceremonia — por eso es el que usarás aquí.

// para reconocerlo, no para usarlo (todavía)

¿Y GitFlow clásico?

GitFlow (Vincent Driessen, 2010) define ramas de larga duración separadas: develop, release/*, hotfix/*, además de main. Fue muy popular porque encaja bien con releases programados y versionados (software empaquetado, firmware, librerías con versiones semánticas que varios consumidores fijan).

Hoy se usa menos para servicios web con despliegue continuo — es más ceremonia de la que la mayoría de equipos necesita, y sus ramas largas generan justo el problema de conflictos que GitHub Flow evita. Sigue siendo razonable si tu software se distribuye (una librería en PyPI, un binario de C++) y necesitas mantener varias versiones mayores en paralelo — vale la pena reconocerlo, aunque este curso no lo use como flujo por defecto.

Autoevaluación

Pregunta 1 de 5

Tu equipo despliega a producción varias veces al día y quiere minimizar ramas largas que generen conflictos grandes, a costa de invertir en feature flags. ¿Qué estrategia describe mejor esa elección?

Correcto: Trunk-Based Development es exactamente ese trade-off — ramas de horas, integración muy frecuente a main, funcionalidad incompleta oculta tras feature flags en vez de aislada en una rama larga.
Pregunta 2 de 5

En GitHub Flow, ¿qué estado debe mantener siempre la rama main?

Correcto: es la primera regla de GitHub Flow. Todo el resto del flujo (ramas cortas, PRs, CI) existe para proteger esa invariante.
Pregunta 3 de 5

Según lo visto en esta página, ¿cuál es la causa número uno de conflictos de merge grandes y dolorosos?

Correcto: cuanto más tiempo vive una rama sin integrarse, más cambios en paralelo acumula main mientras tanto — y más grande es el conflicto al fusionar.
Pregunta 4 de 5

¿Qué mecanismo usa Trunk-Based Development para integrar código incompleto directamente a main sin exponerlo a los usuarios finales?

Correcto: el código vive en main ya, pero apagado detrás de un flag — se activa cuando la feature está lista, sin necesidad de una rama larga esperando.
Pregunta 5 de 5

¿En qué escenario sigue siendo razonable usar GitFlow clásico, según lo visto en esta página?

Correcto: GitFlow encaja con releases programados y versionados (librerías, firmware) donde varios consumidores fijan una versión específica — no con despliegue continuo.
