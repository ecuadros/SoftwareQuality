Qué es BDD y para qué sirve Gherkin

Behavior-Driven Development extiende TDD (Módulo 3) hacia un lenguaje compartido entre quien define el negocio y quien programa. En vez de que el requisito viva solo en la cabeza de una persona ("el descuento debería aplicarse... creo que así"), se escribe como un escenario ejecutable usando Gherkin: Given (dado un contexto), When (cuando ocurre una acción), Then (entonces se espera un resultado).

La especificación es el test. No es documentación que se desactualiza — si el comportamiento cambia y nadie actualiza el escenario, el test falla y lo hace evidente. Eso es lo que la diferencia de un documento de requisitos tradicional.

Python — Behave

Behave ejecuta el archivo .feature tal cual, palabra por palabra, contra "step definitions" en Python que implementan cada línea. Es una de las dos herramientas de este módulo que corren Gherkin de forma literal — la otra es Cucumber-JVM en Java, más abajo — cada una con step definitions en su propio lenguaje.

features/steps/carrito_steps.py
from behave import given, when, then
from carrito import Carrito

@given('un carrito con un monto total de {monto:g}')
def step_impl(context, monto):
    context.carrito = Carrito(monto_total=monto)

@given('un cupón "{codigo}" válido que otorga {porcentaje:d}% de descuento')
def step_impl(context, codigo, porcentaje):
    context.cupon = Cupon(codigo, porcentaje, expirado=False)

@when('el cliente aplica el cupón "{codigo}" al carrito')
def step_impl(context, codigo):
    context.resultado = context.carrito.aplicar_cupon(context.cupon)

@then('el monto total del carrito debe ser {monto:g}')
def step_impl(context, monto):
    assert context.carrito.monto_total == monto

C++ — GoogleTest fixtures + CTest

Diferencia importante: el ecosistema de C++ no tiene un corredor de Gherkin maduro y ampliamente adoptado como Behave. En vez de forzar una herramienta poco mantenida, la práctica equivalente en C++ es usar fixtures de GoogleTest (TEST_F) con nombres que reflejan explícitamente la estructura Given-When-Then del mismo escenario de negocio — el comportamiento especificado es idéntico, el formato de archivo .feature no se usa.
test_carrito.cpp
#include <gtest/gtest.h>
#include "carrito.h"

class CarritoConCupon : public ::testing::Test {
protected:
    // "Given": el contexto compartido por los escenarios de este fixture
    Carrito carrito{120.00};
};

TEST_F(CarritoConCupon, CuponValidoAplicaDescuento) {
    // Given un cupón "VIP10" válido que otorga 10% de descuento
    Cupon vip10("VIP10", 10, /*expirado=*/false);

    // When el cliente aplica el cupón al carrito
    carrito.aplicarCupon(vip10);

    // Then el monto total del carrito debe ser 108.00
    EXPECT_DOUBLE_EQ(carrito.montoTotal(), 108.00);
}

TEST_F(CarritoConCupon, CuponExpiradoEsRechazado) {
    Cupon viejo("PROMO-VIEJO", 20, /*expirado=*/true);

    bool aceptado = carrito.aplicarCupon(viejo);

    EXPECT_FALSE(aceptado);
    EXPECT_DOUBLE_EQ(carrito.montoTotal(), 120.00);
}

Flutter/Dart — integration_test y golden tests

En Flutter, la forma natural de expresar este mismo escenario de negocio a nivel de comportamiento observable es un test de integración de widgets: en vez de llamar directamente a la lógica, simula lo que el usuario realmente ve y toca — escribir el código de cupón y presionar "Aplicar".

integration_test/carrito_cupon_test.dart
import 'package:flutter_test/flutter_test.dart';
import 'package:integration_test/integration_test.dart';
import 'package:mi_app/main.dart' as app;

void main() {
  IntegrationTestWidgetsFlutterBinding.ensureInitialized();

  testWidgets('cupón válido aplica el descuento al monto total', (tester) async {
    // Given un carrito con un monto total de 120.00 (estado inicial de la app)
    app.main();
    await tester.pumpAndSettle();
    expect(find.text('S/ 120.00'), findsOneWidget);

    // When el cliente aplica el cupón "VIP10"
    await tester.enterText(find.byKey(const Key('campo-cupon')), 'VIP10');
    await tester.tap(find.byKey(const Key('boton-aplicar-cupon')));
    await tester.pumpAndSettle();

    // Then el monto total del carrito debe ser 108.00
    expect(find.text('S/ 108.00'), findsOneWidget);
  });
}

Un golden test complementa esto verificando que el widget del resumen del carrito se ve exactamente como se espera tras aplicar el cupón — comparando un render actual contra una imagen de referencia ("golden file") guardada en el repo:

bash
$ flutter test --update-goldens   # genera la imagen de referencia la primera vez
$ flutter test                    # compara contra la referencia en cada corrida siguiente

Java/Spring Boot — Cucumber-JVM

A diferencia de C++, el ecosistema Java sí tiene un corredor de Gherkin maduro y ampliamente adoptado en la industria: Cucumber-JVM. Corre el mismo archivo carrito.feature de arriba tal cual, contra step definitions escritas en Java.

src/test/java/CarritoSteps.java
import io.cucumber.java.es.Dado;
import io.cucumber.java.es.Cuando;
import io.cucumber.java.es.Entonces;
import static org.junit.jupiter.api.Assertions.assertEquals;

public class CarritoSteps {

    private Carrito carrito;
    private Cupon cupon;

    @Dado("un carrito con un monto total de {double}")
    public void unCarritoConMontoTotal(double monto) {
        carrito = new Carrito(monto);
    }

    @Dado("un cupón {string} válido que otorga {int}% de descuento")
    public void unCuponValido(String codigo, int porcentaje) {
        cupon = new Cupon(codigo, porcentaje, false);
    }

    @Cuando("el cliente aplica el cupón {string} al carrito")
    public void elClienteAplicaElCupon(String codigo) {
        carrito.aplicarCupon(cupon);
    }

    @Entonces("el monto total del carrito debe ser {double}")
    public void elMontoTotalDebeSer(double monto) {
        assertEquals(monto, carrito.getMontoTotal(), 0.01);
    }
}

$ mvn test

Cucumber-JVM trae paquetes de anotaciones traducidas — io.cucumber.java.es usa @Dado/@Cuando/@Entonces en vez de @Given/@When/@Then, pensado exactamente para proyectos que, como este curso, escriben sus escenarios en español. En un proyecto Spring Boot real, estas step definitions suelen anotarse además con @SpringBootTest para correr contra el contexto real de la aplicación, en vez de contra objetos de dominio sueltos como en este ejemplo mínimo.

Lo que cada stack sí y no puede hacer

Python (Behave)C++ (GoogleTest fixtures)Flutter/Dart (integration_test)Java/Spring Boot (Cucumber-JVM)
¿Corre Gherkin literal?Sí — el .feature es el testNo — el escenario se traduce a nombres de test y comentariosNo — el escenario se traduce a pasos de interacción con la UISí — el mismo .feature, con step definitions en Java
Nivel probadoLógica de negocio directaLógica de negocio directaUI completa, como la usa el usuarioLógica de negocio directa (o el contexto completo de Spring, si se anota con @SpringBootTest)
Riesgo si se fuerza la herramienta "equivalente"—Adoptar un runner de Gherkin poco mantenido solo por "consistencia" añade fragilidad sin beneficio realUsar solo pruebas de lógica pura perdería la cobertura del flujo real de UI, que es donde más bugs de integración aparecen en apps móviles—
La lección de este módulo no es "Gherkin en todos lados a la fuerza" — es que el mismo comportamiento de negocio se puede especificar de forma ejecutable con la herramienta que mejor encaja en cada ecosistema, sin perder precisión ni cobertura. Que Python y Java sí tengan un corredor de Gherkin maduro, y C++ no, es una propiedad del ecosistema — no un juicio sobre qué lenguaje es "mejor" para BDD.

Pregunta 1 de 6

¿Cuáles DOS de los cuatro stacks vistos en esta página ejecutan el archivo .feature de Gherkin de forma literal?

Correcto: Behave (Python) y Cucumber-JVM (Java) corren el archivo .feature palabra por palabra, cada uno contra step definitions en su propio lenguaje. C++ y Flutter/Dart expresan el mismo comportamiento con otras herramientas, sin un archivo .feature de por medio.
Pregunta 2 de 6

Según esta página, ¿por qué C++ no usa un corredor de Gherkin literal para expresar el mismo escenario?

Correcto: forzar una herramienta poco mantenida "solo por consistencia" entre stacks añade fragilidad sin beneficio real — la elección correcta es la práctica equivalente y bien soportada en cada ecosistema, no la sintaxis idéntica a toda costa.
Pregunta 3 de 6

En el test de Flutter/Dart mostrado, ¿qué nivel del sistema se está probando, a diferencia de la versión en Python?

Correcto: integration_test con WidgetTester ejercita la app completa a través de su interfaz, a diferencia de Behave, que llama directamente a la lógica de negocio en Python.
Pregunta 4 de 6

¿Qué verifica específicamente un golden test en Flutter que un test de lógica pura no verifica?

Correcto: un golden test compara el render actual del widget contra una captura de referencia ("golden file"), detectando regresiones visuales que un test de lógica no puede ver.

Correcto: BDD es una forma de pensar y especificar comportamiento, no una sintaxis obligatoria — la herramienta correcta es la que encaja mejor en cada ecosistema sin sacrificar cobertura ni claridad.
