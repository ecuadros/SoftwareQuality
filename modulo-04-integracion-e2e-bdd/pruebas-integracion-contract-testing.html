El bug que ningún test unitario atrapa

Imagina dos equipos: uno construye el servicio de pagos, otro construye el carrito de compras que lo consume. Cada equipo mockea al otro en sus tests unitarios (Módulo 3) — es lo correcto, así deben ser los tests unitarios. El servicio de pagos cambia el campo monto de centavos (entero) a dólares (decimal) en una nueva versión, actualiza sus propios tests unitarios, y los deja en verde. El carrito sigue mockeando la respuesta vieja, así que sus tests unitarios también siguen en verde.

Los dos equipos tienen 100% de tests unitarios pasando — y el sistema integrado está completamente roto: el carrito le está cobrando a un cliente 100 veces menos de lo que debería. Ningún test unitario, por diseño, iba a atrapar esto: ambos mockearon exactamente la parte que cambió.

Esto no es un fallo de los tests unitarios — es exactamente lo que se supone que hagan (aislar). El problema es depender solo de ellos. Este módulo cubre las capas de prueba que sí atrapan este tipo de falla: integración, contract testing, BDD y E2E.

La pirámide de pruebas

No todas las capas de prueba deben tener la misma cantidad de tests. La pirámide de pruebas (Mike Cohn) es una guía de proporción: muchos tests rápidos y baratos en la base, pocos tests lentos y caros en la punta.

CapaCantidad relativaVelocidadQué verifica
E2E (Módulo 4)Pocos (decenas)Lenta (segundos a minutos por test)El sistema completo, como lo usa un usuario real, de punta a punta.
Integración (esta página)Moderada (cientos)MediaQue dos o más componentes reales colaboran correctamente entre sí.
Unitarias (Módulo 3)Muchas (miles)Muy rápida (milisegundos)Una unidad de lógica, aislada de todo lo demás.
El error inverso también existe: un equipo que solo confía en E2E porque "prueba todo de verdad" termina con una suite lentísima y frágil (un test E2E falla por timing, por datos de prueba compartidos, por cambios de UI ajenos a la lógica) que tarda tanto en correr que deja de ejecutarse en cada cambio — perdiendo justo la propiedad de "Timely" del Módulo 3.
// la capa del medio

Qué prueba realmente una prueba de integración

Una prueba de integración verifica que dos o más componentes reales — no mockeados — colaboran correctamente: tu código de acceso a datos contra una base de datos real (o un contenedor efímero de la misma), tu cliente HTTP contra una API real, dos módulos internos de tu propio sistema trabajando juntos sin dobles de prueba de por medio.

Test unitarioTest de integración
Base de datosMockeada o en memoria (fake)Real (o contenedor Docker efímero con datos de prueba)
Pregunta que responde¿Esta función calcula bien, dado un input?¿Esta función realmente guarda y recupera bien de la base de datos real?
Falla típica que atrapaLógica de negocio incorrecta.Query SQL mal escrita, tipo de dato incompatible, configuración de conexión rota.

En el stack Java/Spring Boot de este curso, el "contenedor Docker efímero con datos de prueba" de la tabla de arriba tiene nombre propio: Testcontainers. Levanta una instancia real de MongoDB en Docker solo para la duración del test — nada de una base de datos compartida entre corridas, ni de un fake que se comporte distinto al motor real.

src/test/java/CarritoRepositoryIT.java
@SpringBootTest
@Testcontainers
class CarritoRepositoryIT {

    @Container
    static MongoDBContainer mongo = new MongoDBContainer("mongo:7.0");

    @DynamicPropertySource
    static void mongoProps(DynamicPropertyRegistry registry) {
        registry.add("spring.data.mongodb.uri", mongo::getReplicaSetUrl);
    }

    @Autowired
    private CarritoRepository carritoRepository;

    @Test
    void guardaYRecuperaUnCarritoReal() {
        Carrito guardado = carritoRepository.save(new Carrito(120.00));

        Carrito recuperado = carritoRepository.findById(guardado.getId()).orElseThrow();

        assertEquals(120.00, recuperado.getMontoTotal());
    }
}
CarritoRepository aquí es una interfaz de Spring Data MongoDB — sin una sola línea de código de acceso a datos escrita a mano. El test de integración confirma que esa capa de persistencia generada automáticamente realmente funciona contra un MongoDB real, no contra una suposición de cómo debería comportarse.

Contract testing: el problema del ejemplo inicial, resuelto

El contract testing ataca exactamente el escenario de pagos vs. carrito de la introducción — y no es casualidad que sea justo ahí donde más se necesita. En una arquitectura de microservicios, cada servicio se despliega de forma independiente, en su propio momento, por su propio equipo. Nadie coordina un "gran release" donde todos los servicios cambian juntos — lo que significa que el problema de "el proveedor cambió el formato y el consumidor no se enteró" no es una excepción, es el riesgo estructural número uno de este estilo de arquitectura.

En vez de que cada equipo mockee al otro "a mano" (con el riesgo de que el mock quede desactualizado), ambos equipos comparten un contrato explícito — un archivo que describe la forma exacta de la request/response esperada — a través de un Pact Broker, un servicio central que coordina el intercambio:

PasoQuién lo haceQué produce
1Equipo consumidor (carrito)Corre su test de contrato, genera un archivo pact (JSON) con las interacciones que su código realmente espera.
2Equipo consumidor, en su CI (Módulo 5)Publica ese pact al Pact Broker compartido.
3Equipo proveedor (pagos), en su propio CIDescarga los pacts publicados por sus consumidores y los verifica contra su implementación real.
4Pact BrokerRegistra si esa versión del proveedor cumple el contrato de cada consumidor conocido.
5Cualquiera de los dos equipos, antes de desplegarPregunta al broker can-i-deploy — "¿es seguro desplegar esta versión, dado lo que ya está en producción del otro lado?"
src/test/java/CarritoConsumerPactTest.java — equipo consumidor
@ExtendWith(PactConsumerTestExt.class)
class CarritoConsumerPactTest {

    @Pact(consumer = "carrito-service", provider = "pagos-service")
    public RequestResponsePact procesarPago(PactDslWithProvider builder) {
        return builder
            .given("el monto es válido")
            .uponReceiving("una solicitud de pago")
                .path("/pagos").method("POST")
                .body("{\"monto\": 108.00}")
            .willRespondWith()
                .status(200)
                .body("{\"estado\": \"aprobado\", \"monto\": 108.00}")
            .toPact();
    }

    @Test
    @PactTestFor(pactMethod = "procesarPago")
    void elCarritoProcesaUnPagoAprobado(MockServer mockServer) {
        // llama al mock generado por Pact en mockServer.getUrl() y verifica la respuesta
    }
}
bash — equipo proveedor, verificando el pact publicado
$ mvn pact:verify
# Verifying a pact between carrito-service and pagos-service
# Given el monto es válido
#   una solicitud de pago
#     returns a response which
#       has status code 200 (OK)
#       has a matching body (OK)

$ pact-broker can-i-deploy --pacticipant pagos-service --version 2.4.0 --to-environment produccion
# Computer says yes \o/ — todos los consumidores conocidos verificaron esta versión
can-i-deploy es la pieza que conecta este módulo con el Módulo 5: se agrega como paso obligatorio del pipeline antes del job de deploy, para cada servicio. Si algún consumidor todavía no verificó esa versión — o la verificó y falló — el despliegue se bloquea automáticamente, sin depender de que alguien recuerde coordinar manualmente entre equipos.
Para el proyecto de este curso, con un equipo pequeño, montar un Pact Broker completo puede ser más infraestructura de la que hace falta. La versión práctica y suficiente sigue siendo válida: un archivo de esquema compartido (JSON Schema u OpenAPI) que ambos lados validan en su propio CI. Lo importante es entender el mecanismo — contrato explícito, verificado por el proveedor, que bloquea el despliegue si se rompe — más que la herramienta específica.

Autoevaluación

Pregunta 1 de 7

En el ejemplo de pagos y carrito, ambos equipos tenían 100% de tests unitarios en verde y el sistema integrado seguía roto. ¿Por qué los tests unitarios no atraparon el problema?

Correcto: aislar dependencias con mocks es correcto para tests unitarios (Módulo 3), pero implica que un cambio de contrato entre dos servicios reales nunca se detecta ahí — para eso existen la integración y el contract testing.
Pregunta 2 de 7

Según la pirámide de pruebas de Mike Cohn, ¿cómo debería distribuirse la cantidad de tests entre capas?

Correcto: la forma de pirámide refleja que los tests rápidos y baratos (unitarios) deben ser mayoría, mientras que los lentos y frágiles (E2E) deben usarse con moderación, solo para lo más crítico.
Pregunta 3 de 7

Un equipo confía casi exclusivamente en tests E2E porque "prueban todo de verdad". Según lo visto en esta página, ¿qué problema práctico genera esto?

Correcto: los tests E2E son valiosos pero lentos y sensibles a factores ajenos a la lógica (timing, datos compartidos, UI). Depender solo de ellos rompe el principio "Timely" visto en el Módulo 3.
Pregunta 4 de 7

¿Cuál es la diferencia clave entre un test unitario y un test de integración sobre el mismo código de acceso a datos?

Correcto: la presencia de una dependencia real (no mockeada) es exactamente lo que distingue a una prueba de integración de una unitaria — y lo que le permite atrapar fallas como un query SQL mal escrito.
Pregunta 5 de 7

En contract testing, ¿qué logra que el equipo proveedor corra el contrato del consumidor en su propio pipeline de CI?

Correcto: es la aplicación directa del "shift left" del Módulo 1 — mover la detección del defecto de contrato al momento más temprano posible: el CI del propio proveedor, no producción.
Pregunta 6 de 7

En el ejemplo de CarritoRepositoryIT con Testcontainers, ¿qué logra levantar un MongoDBContainer real en Docker, en vez de usar un mock o un fake en memoria?

Correcto: es exactamente la definición de prueba de integración de esta página — verificar contra una dependencia real, no mockeada. Testcontainers da esa base de datos real de forma efímera, sin compartir estado entre corridas ni depender de un servidor MongoDB fijo en la máquina de cada desarrollador.
Pregunta 7 de 7

El equipo de pagos-service quiere desplegar su versión 2.4.0 a producción. Según el mecanismo de Pact Broker descrito en esta página, ¿qué verifica el comando can-i-deploy antes de permitirlo?

Correcto: can-i-deploy responde específicamente "¿es seguro desplegar esto, dado lo que ya está en producción del otro lado?" — consultando en el broker si los consumidores conocidos ya verificaron esa versión exacta del contrato, no otros aspectos de calidad como cobertura o linters.
