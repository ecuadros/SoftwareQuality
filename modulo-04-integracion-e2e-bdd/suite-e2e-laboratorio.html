Qué es (y qué no es) una prueba E2E

Una prueba End-to-End ejercita el sistema completo tal como lo usaría un usuario real: sin mocks, sin dobles de prueba, contra una instancia real (o casi real) de todo el stack — base de datos, API, y en el caso de Flutter, la app corriendo de verdad en un dispositivo o emulador.

Cómo elegir cuáles escenarios merecen ser E2E

Como viste en la pirámide de pruebas (página anterior de este módulo), la punta debe tener pocos tests. La pregunta correcta no es "¿qué más puedo probar E2E?" sino "¿qué flujo, si se rompe, es tan grave que justifica el costo de mantenimiento de un test E2E?"

Buenos candidatos a E2E: los "happy paths" críticos para el negocio (completar una compra, iniciar sesión, guardar el trabajo del usuario) y quizás uno o dos casos de error graves (pago rechazado). Malos candidatos: validaciones de campo por campo, casos límite numéricos, combinaciones exhaustivas de inputs — eso ya lo cubren, mucho más barato, los tests unitarios (Módulo 3) e integración.

Autoevaluación

Pregunta 1 de 5

¿Qué distingue principalmente a una prueba E2E de una prueba de integración, según esta página?

Correcto: la E2E cubre el flujo completo (agregar al carrito, aplicar cupón, pagar) mientras que la integración prueba una interacción puntual (por ejemplo, el acceso a datos contra la base real).
Pregunta 2 de 5

Según el criterio de esta página para elegir qué automatizar como E2E, ¿cuál de estos es un BUEN candidato?

Correcto: los "happy paths" críticos para el negocio son buenos candidatos a E2E. Las validaciones exhaustivas de campo o casos límite numéricos son mucho más baratas de cubrir con tests unitarios.
Pregunta 3 de 5

¿Por qué el laboratorio de esta página pide automatizar como máximo 1-2 flujos E2E, y no todos los flujos posibles del proyecto?

Correcto: coherente con la pirámide de pruebas vista en la página anterior — pocos E2E, elegidos deliberadamente por su criticidad, no exhaustivamente.
Pregunta 4 de 5

Según el checklist de cierre del Módulo 4, ¿qué proporción debería tener la suite de pruebas del proyecto?

Correcto: es la aplicación práctica de la pirámide de pruebas al propio proyecto del curso — se audita exactamente esa proporción en la rúbrica de cierre del módulo.
Pregunta 5 de 5

Un test de integración prueba dos módulos internos de tu propio sistema sin usar dobles de prueba entre ellos. ¿Qué requisito del checklist de esta página cumple?

Correcto: como se definió en la página anterior del módulo, una prueba de integración puede ser entre dos módulos internos reales, sin necesidad de una base de datos o API externa — lo que importa es la ausencia de dobles de prueba entre los componentes evaluados.
